## Verdict, in one line

(chroma-only, at frame HEIGHT 242) and 3 panic (every `--lossless=1` 4:2:2

  For the table I used a local COUNTING variant of the same two views (it

  process); it is the same file pair, the same rungs, the same plane split.

**Control, batch level, both green on this tree before any cell was measured:**

- `the_counting_oracle_diff_detects_one_flipped_oracle_byte` — pass.
  "baseline exact, each flipped oracle byte reported as exactly 1".
- `every_oracle_comparator_reds_on_a_one_byte_wrong_oracle` — pass. All five
  oracle comparators go RED on a one-byte-wrong oracle. This is the permanent
  control for the exact defect that got `lanes/av1422remeasure.report.md`
  retracted.

**Control, per cell, on the SAME comparator that produced the table.** Every
cell was measured four times with the same two helpers: once clean, and three
more times with ONE bit flipped in the ORACLE's own bytes — at the first
luma byte, the first U byte and the first V byte of frame 0. The flip
indices come from the first decoded picture, so the three controls really do
land in the three planes. A cell that reads 0 wrong clean and 0 wrong
flipped would be a comparator that had stopped reading the oracle; that does
not occur once in 30 cells. The per-cell `ctrl@` columns below carry it, and
the decode-order view carries its own `dctrl=` (same three flips, re-counted
against the `EC_AV1_FINAL_DUMP` frame 0). For an exact cell every control
reads `[1,0,0] [0,1,0] [0,0,1]` and `dctrl=[(..,1), (..,1), (..,1)]`; for a
diverging cell the control is that cell's own wrong-count plus exactly one,
in the right plane.

### Encoder recipe, and the two y4m traps

```
aomenc --codec=av1 --profile=2 --input-bit-depth=<bd> --bit-depth=<bd> \
       --limit=16 --lag-in-frames=25 --auto-alt-ref=1 --enable-global-motion=1 \
       --pass=1 --cq-level=24 --threads=4 --kf-min-dist=0 --kf-max-dist=999999 \
       --width=W --height=H --cpu-used=0 <src>.y4m -o <n>.webm
ffmpeg -v error -i <n>.webm -c copy -f obu <n>.obu -y
```

Per-cell deltas are named in the table. Two y4m traps cost real time and are
worth writing down:

1. libaom's y4m reader **requires the `YUV4MPEG2 ` magic**. A hand-built
   header without it parses, finds the tags, and then encodes as 4:2:0 —
   which surfaces as `Profile 2 bit-depth <= 10 requires 4:2:2 color format`,
   a message that reads like a 4:2:2 problem and is not one.
2. The 4:2:2 chroma tag is **lowercase-p** at high bit depth: `C422p10`,
   `C422p12`. `C422P10` is silently not `422p10`, and with the magic present
   a wrong-case tag encodes 12-bit 4:2:0 rather than failing.

## Narrowing the four divergences

**Stage.** `Q_odd320x242`, both sides, oracle rung `EC_AV1_PREFILT_DUMP` (Y
then U then V, crop-sized rows, after tile decode, **before** deblock, CDEF and
LR) against the decoder's own rung of the same name:

```
frame 0..16: 154880 bytes each side, 31557 / 37686 / 48432 / 48123 / 47905 /
            50654 / 49788 / 49822 / 49191 / 52843 / 51434 / 51248 / 52016 /
            53004 / 53146 / 52939 / 53133 differing bytes
```

Every decode-order frame differs already at PREFILT, so **deblock, CDEF and
loop restoration are exonerated**; the defect is in reconstruction.

**Plane and region**, same dumps, frame 0 (the keyframe):

```
Y (320x242, bytes 0..77440)      differing = 0        <- luma byte-exact
U (160x242, bytes 77440..116160) differing = 14722
    first byte 0 -> chroma (row 0, col 0): ours 81, oracle 224
    rows touched 232 of 242 (0..231), cols touched 160 of 160
V (160x242, bytes 116160..154880) differing = 16835
    first byte 0 -> chroma (row 0, col 0): ours 90, oracle 166
    rows touched 242 of 242, cols touched 160 of 160
```

So on this cell the whole 4:2:2 chroma plane of the **keyframe** is wrong from
its top-left sample, with luma byte-exact, before any loop filter. The other
three diverging cells carry the same shape with the same first-divergent
plane: `O` at U(0,0)-equivalent byte 106388 (plane 1), `S` at byte 214112
(plane 1), `AB` at byte 80671 (plane 1) — all plane 1, all frame 0.

**Axis.** Frame height, not width, and not a tiling accident:

- `R_odd322x240` (odd **width** 322, height 240): exact.
- `Q_odd320x242` / `O_odd322x242` / `S_odd326x242_10b` (height **242**,
  three widths, two bit depths): all diverge.
- `V_tile2x2_odd` is 322x**242** and **exact** — so the trigger is not
  "height 242" alone; tiling changes the block layout enough to dodge it.
  That is the same "not a simple alignment rule" the 4:2:0 defect showed, and
  it means the trigger is a per-superblock or per-row-band extent whose
  remainder is handled for some remainders and not others.

**What this is not.** It is not an entropy desync: luma is byte-exact
pre-filter on every frame, and a parse desync would not leave 320x240 luma
untouched across 17 frames. It is not a loop-filter effect (PREFILT). It is
not the retired 4:2:0 defect (4:2:0 at 242 is exact). It is a 4:2:2 chroma
reconstruction defect whose trigger is a frame-height remainder.

## Narrowing the three panics

All three `--lossless=1` 4:2:2 cells panic at the same line, `decode.rs:37565`
inside `read_inter_chroma_lossless` (backtrace: `read_inter_chroma_lossless` →
`decode_inter_block` → `decode_inter_frame_tile_with_cdfs`):

```
range end index 20 out of range for slice of length 16
```

The copy is

```rust
let dst = mu_units(<plane>, stride * stride);
for row in 0..4 {
    let start = (oy + row) * stride + ox;
    dst[start..start + 4].copy_from_slice(&cu_grid[row * 4..][..4]);
}
```

`stride` is documented at the call site as "the block's **square** chroma
side, even for a 2:1 strip, which embeds its narrower plane block in the same
square grid". For an 8x8 lossless inter leaf, 4:2:2 gives a chroma plane block
of **4 wide x 8 tall** — not square — so the scratch is `4*4 = 16` while the
walk covers `4*8 = 32`; the second 4-row band starts at element 20. 4:2:0 and
4:4:4 have square chroma plane blocks at that leaf size, so the arm's own
`stride` contract is only violated by 4:2:2. That is why all three lossless
cells panic and no 4:2:0 or 4:4:4 cell does.

**This is a panic, not wrong pixels.** A panic in a decoder reachable through
a lifted refusal is a strictly worse failure mode than a refusal, and it is
the one finding in this report that a lift would expose to ordinary input.

inter, not to this one — I am naming it, not claiming it.

## Recommendation

**Keep the refusal. It is still earning its keep, but for two concrete,
narrow, fixable reasons rather than the old coverage argument.** On this
evidence: 23 of 30 reachable 4:2:2 cells are byte-exact against the
instrumented `aomdec` in both the presented and the decode-order view, with
per-cell oracle-flip controls on every one — the 4:2:2 decoder is in good
shape. But **every 4:2:2 cell at frame height 242 that I could produce
diverges** (4 of 4: `O`, `Q`, `S`, `AB`, up to 22 988 wrong presented samples,
whole chroma plane of the keyframe, luma exact, present pre-loop-filter), and
**every `--lossless=1` 4:2:2 cell panics** (3 of 3, at one named line,
`decode.rs:37565`, for a reason that is arithmetically 4:2:2-only). Lifting
would expose users to chroma-only corruption on a whole family of ordinary
heights and to a decoder panic on lossless content. The deciding numbers are
**4/4 diverging at height 242 and 3/3 panicking on lossless**, against
**23/23 exact everywhere else**; the height-242 4:2:0 controls at the same
widths are exact, so this is not a defect 4:2:0 shares, and the retraction's
premise that it was the shared odd-height 4:2:0 defect no longer holds now
that `lane-av1422chrtx` has fixed that one. What I would do next, in order:
(1) fix `read_inter_chroma_lossless`'s `stride` for a non-square 4:2:2 plane
block — it is a one-line extent and the panic is loud; (2) sweep 4:2:2 frame
heights 232/234/…/250 at one width to map the remainder trigger, which also
tells us whether `V_tile2x2_odd`'s exactness is a dodge or a different path;
(3) re-run this table, and only then decide between a narrowed refusal and a
lift. I am not changing the refusal string or the header behaviour: that is a
shipped-capability call, and the honest input to it is that 7 of 30 cells are
not exact today.

  `EC_AV1_FINAL_DUMP` views `decode_all_frames_vs_oracle` uses, with its own
  per-plane oracle-flip control.

**No new instrumentation was added to the decoder or the oracle.** The stage
ladder used the pre-existing `EC_AV1_PREFILT_DUMP` rung on both sides.

## `not_done`

- **12-bit 4:2:2 is unreachable with this `aomenc`.** `aomenc --profile=2
  --bit-depth=12` on a correct `C422p12` y4m fails with `Failed to set chroma
  subsampling x: Unspecified internal error`. It is unwitnessed, not untried.
  (Note: an earlier attempt with a wrong-case `C422P12` tag *appeared* to
  succeed and produced a 13 961-byte OBU — that stream was not 4:2:2 and was
  discarded. The lowercase-p tag is the real requirement.)
- **Superres 4:2:2 unwitnessed.** `--superres-mode=2` produced no encode with
  this build; no recipe found.
- **No fixture committed.** The 24 fresh cells are recorded above with full
  recipes and sha256 but are not pinned into `crates/ec-av1/fixtures/`.
  Pinning belongs with whichever cell becomes a gate, not with this report.
- **The height-242 trigger is not root-caused.** It is localised to 4:2:2
  chroma reconstruction (PREFILT, keyframe, luma exact, plane 1 first) and to
  a height remainder, and the full width x height grid is not swept, so the
  trigger's real extent is unknown. `V_tile2x2_odd` being exact at 322x242
  means "height 242" is not the whole rule.
- **The `read_inter_chroma_lossless` extent fix is not made.** The panic site
  and the arithmetic are named; shipping a speculative change to a bit-exact
  decoder on one cell family is not this lane's call.
- **The 4:2:0 lossless alt-ref + global-motion divergence is named, not
  owned.** It is swept above to the recipe delta that triggers it and left for
  the lossless-inter owner.
- **The top-half engagement census was not re-run** (oracle-side libaom
  instrumentation I did not rebuild).
- **Full suite not run** (lane rules: scoped only; project-wide validation is
  Main's).
