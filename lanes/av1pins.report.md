# lane-av1pins — recover three lost pins, correct a stale blocker comment, measure the mandelbrot claim

Branch `lane-av1pins`, worktree `~/.cache/wt/av1pins`, base `a21f3680` (the merged
seven-lane main). Comment, fixture and test changes only — **no decoder logic**.
Commits: `78c805bd` (pins + gate rewiring + comment correction), plus this report.

The headline is that the third of those reversed my own prior conclusion: the
mandelbrot blocker is measurably **cleared**, and the comment that recorded it as
the live blocker was the stale artefact, not the `#[ignore]` string.

---

## 0. The root cause, which is structural and not per-pin

`.gitignore:2` is a bare `fixtures`, which git matches at **any depth** — so it
covers `crates/ec-av1/fixtures/` too, not just the root. The 48 pins already
tracked there were force-added. Any *new* pin therefore has to be `git add -f`'d
or it is silently uncommittable, and any pin written to the root `fixtures/` is
uncommittable by construction.

`pin_dir()` resolves to the root (`../../fixtures`, gitignored), which is where
all three dead pins were written. `lanes/av1skipfix.report.md` had already
recorded this and had listed exactly these three as "missing on this box". So the
diagnosis predates this lane; what was missing was the recovery.

The fix is `crate_pin(name)` (`crates/ec-av1/src/stream.rs:8670`): prefer the
committed `crates/ec-av1/fixtures/<name>`, fall back to `pin_dir()` so a locally
re-captured stream still overrides. The committed copy is what runs by default.

## 2. Before / after, per gate

All runs `--release`, `--test-threads=1`, oracle present.

| gate | before | after |
|---|---|---|
| `pinned_golden3_stream_decodes_pixel_exact` | `SKIP ... no pinned bytes`, **0.00s**, `rc=0` | `1 passed`, **0.15s**, prints `4 frame(s) byte-exact vs ffmpeg from .../crates/ec-av1/fixtures/golden3-pin.obu` |
| `pinned_sbpart_stream_decodes_pixel_exact` | `SKIP ... no pinned bytes`, **0.00s**, `rc=0` | `1 passed`, **0.15s**; `EC_SBPART_DIAG=1`: `DIAG frame 0: 0 luma mismatches, bbox ... of 192x128` + per-SB-column counts for cols 0..64, 64..128, 128..192 |
| `a_real_aomenc_lossless_444_key_frame_decodes_sample_exact` | `SKIP ... no pinned bytes`, **0.05s**, `rc=0` | `1 passed`, **0.11s** |

**Real work, not a stop-skipping — three independent proofs.**

1. *Self-evidencing output.* sbpart's `EC_SBPART_DIAG` walks all `192*128 =
   24576` luma samples and reports per-superblock-column mismatch counts.
   golden3 prints its frame count and the path it read. A skip prints none of it.
2. *Non-vacuity assertions that had to hold.* ll444 passes `assert!(lossless)` on
   the parsed frame header **and** `assert!(rect_split_lossless_chroma444_hits() >
   before)` — the 4:4:4 chroma rect-split walk provably ran, or the gate would be
   red. That is what makes it a verdict rather than a decode.
3. *Mutation.* One byte flipped mid-pin turns all three RED: golden3
   `stream.rs:5106` (`left: 12288, right: 24576`), sbpart `stream.rs:5099`, ll444
   `stream.rs:6537`. **Stated precisely:** these die in the *ffmpeg decode* step,
   not the pixel compare — a bit-flipped arithmetic-coded stream does not decode.
   So the mutation proves the bytes are READ and PROCESSED (a skip returns `ok` at
   0.00s and never reaches any of it); it does **not** prove the pixel compare is
   what catches a bit flip. Proof 1 covers the compare.

**One assertion added per gate on the way.** Each of the three compared
`frames.iter().zip(&ffmpeg_frames)` with no length check — the exact `cmpaudit`
class, where a short side truncates the walk silently. Each now asserts
`frames.len() == ffmpeg_frames.len()` first, naming the mis-pairing in the message.

The `#[ignore]` reasons changed from "reads a pinned fixture path outside the
repo; run manually" to "bisect aid, not a suite gate; run it with `--ignored`" —
still ignored, but the old text claimed a property (outside the repo) that is no
longer true.

## 3. The stale comment, and the measurement that reversed my own call

Last turn I reported to Main that the two 1:4 gates' `#[ignore]` strings were wrong
and the 22-line comment above them was right. **That was backwards**, and the
re-run says so.

The r2 comment recorded, as these gates' blocker, an unowned mandelbrot
inter-frame defect: "decode-order frame 3/4 luma ~3.7-4.5k samples, max |d| 6..17,
then frames 5-7 drift to ~24k samples, max |d| ~220", plus "seeds 46 and 54 fire
ZERO 1:4 strips ... and mismatch ffmpeg the same way as the firing seed 52".

**Measured on `a21f3680`, release, the r2 recipe set re-run in full** — 40 attempts
per bit depth, from the gate's own parameters (mandelbrot 192x128, `start_scale =
5.0 - attempt*0.06`, `end_pts=8`, `hue=s=0`, `-t 0.32`,
`--enable-rect-partitions=1 --enable-1to4-partitions=1 --min-partition-size=32
--max-partition-size=64 --enable-tx-size-search=0 --enable-filter-intra=1
--enable-intra-edge-filter=1 --kf-min-dist=1000 --kf-max-dist=1000` plus the
standard disable set, `--cpu-used = 1 + attempt%4`, `--cq-level =
[63,55,45,35][(attempt/4)%4]`):

| | 8-bit | 10-bit |
|---|---|---|
| attempts decoded + pixel-compared | **40** | **40** |
| gate's own tally | `counted-exact=0 uncounted-exact=40 named-refusals=0` | identical |
| `first diff at` / `samples differ` / `max \|d\|` lines in the full log | **0** | **0** |
| 1:4 strips in inter frames | `64x16=0 16x64=0 32x8=0 8x32=0` | identical |

Both the frame range and the byte counts r2 named are simply absent: no frame 3/4
counts, no `max |d|`, no drift. **The mandelbrot inter-frame defect is cleared on
this tree** — 80 streams compared, 80 exact. A positive measurement, not the
absence-of-evidence I flagged last turn.

And the recipe moved the other way: **zero** 1:4 strips fire now across all 42
counted attempts per arm, where r2 had one attempt firing `64x16=4 16x64=3`. The
gates went from "fires sometimes, compare fails" to "never fires", and now trip
their own non-vacuity precondition at `stream.rs:40653` rather than any pixel.

**Therefore:** the `#[ignore]` strings are correct for this tree and the comment
was the stale artefact. Both gates stay ignored — a source that is baseline-exact
*and* fires a 32-level intra 1:4 strip in an inter frame still does not exist —
and the comment now records the cleared blocker and the zero-strip recipe
regression, dated, with the reason for the correction.

What I did **not** claim: I did not identify which commit cleared the mandelbrot
defect. The 7-lane wave is the obvious suspect and the measurement is consistent
with it, but "the wave fixed it" is a correlation across a merge, not an
attribution. Closing that needs an ablation, which is a bisect, not a comment fix.

## 2. No condition that makes this crate ignore a gate applies

Measured on `a5867794`, both gate bodies:

* **no process-global** — neither calls `force_sb128` nor `knob_write`. This is the
  condition that legitimately earns 11 other ignores in this crate.
* **no counter, no `lock_gate_counters()`** — so `--test-threads=1` is not required
  of them either.
* **no aomenc** — they decode committed bytes and compare to ffmpeg, so they are not
  real-aomenc gates and stay out of the `gate_coverage` census either way.
* **not slow** — 0.10–0.15 s each, against 9 ignored siblings that declare
  minutes-per-item.
* **ffmpeg guarded** — `have_ffmpeg()` already honours `EC_AV1_REQUIRE_FFMPEG`, so a
  missing ffmpeg is a hard failure, not a silent skip.

Precedent in-tree: `gate_coverage.rs` records the 10-bit LR gate *"was `#[ignore]`d on
that branch and passes un-ignored on main, which carries the fix"* — the same
un-ignore-once-the-blocker-clears move.

## 4. A regression I caused and then disproved — recorded because it nearly shipped

The first `gate_coverage` run **on this branch** showed
`FAILED. 8 passed; 2 failed` (`never_exercised_8bit_matches_the_gate_recipes`,
`never_exercised_10bit_matches_the_gate_recipes`), while the same filter on main
passed 10/10. Un-ignoring changes the census input, so I took that as a regression
I had introduced.

It was not. A 554-second `--ignored` full-suite run was executing **against the same
worktree and the same `CARGO_TARGET_DIR` at that moment**. Re-run after it finished:
`gate_coverage` **10 passed / 0 failed on 6 consecutive runs**, and alone with
`--exact` it also passes. These are compile-time source scans (`include_str!`),
which cannot be perturbed by runtime state — consistent with a build/link race on
the shared target dir, not with a logic change. Recorded because "I broke a meta-gate"
was the correct reading of the evidence at the time, and the reason it was wrong is
worth keeping.

Final meta-gate state after the change: `gate_coverage` **10 passed**,
`refusal_inventory` **15 passed**, both green.
