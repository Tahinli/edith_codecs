## ROOT CAUSE (fixed, `f9720de`)

libaom codes no chroma transform for a block that is not the chroma reference
of its 4:2:0 pair -- `av1_reset_entropy_context`:
`nplanes = 1 + (num_planes - 1) * xd->is_chroma_ref` -- so such a block leaves
the above/left CHROMA entropy contexts untouched. Our INTER block reader
(`decode.rs`, the `record_split_luma_rect_mi` / `record_rect_mi` pair right
before the `pair_chroma` block, ~line 22955) wrote all three planes
unconditionally, and for a non-chroma-reference strip the chroma grids are the
all-zero ones built in the `!has_chroma` arm. So the EVEN 4x16 strip of the
`PARTITION_VERT_4` at mi(40,220) cleared the real left-neighbour chroma state,
and the PAIR's own `all_zero` then read `txb_skip_ctx` one row low.

Measured, decode-order frame 1 of the 2-frame cut
`~/.cache/inter128intra-tmp/t900_2.obu` (10-bit 1920x792, 128 SB):

| | before | after | aomdec |
|---|---|---|---|
| chroma `all_zero`, entry rng 37582 | ctx base 1 -> rng 37384 | ctx base **2** -> rng **51992** | ctx 9 (2+7) -> **51992** |

`EC_DCDUMP` (now dumping all three planes, not plane 0 only -- without the
chroma cells the wipe is invisible) showed it directly: at strip 220's own
luma read `left[40..43][1] = Some(true)/1`; at strip 221's read the same cells
are `None/0`. The wiper is between them, i.e. strip 220's record.

Fix shape: snapshot planes 1/2 of the block's left/above cells when
`!has_chroma` and restore them after the recorders run -- equivalent to not
writing them, without threading a flag through both recorders.

Sibling sweep (class `context-read-from-one-cell` / `new-map-ignores-tile-edge`):
`decode_rect4_16_strip` writes chroma only under `if has_chroma`; the sub8
intra rect reader early-returns on `!has_chroma` before its chroma block;
`decode_leaf_rect8`/`decode_leaf_split4` use `record_mi_luma*` (plane 0 only).
The inter reader was the only unguarded site.

  (aom - ours = -2, no dither at all); the bottom 32x16 (rows 112..127, which
  does carry residual) is a dithered mix of 0/-1/-2.
* NOTE the trace disagreement worth one check first: aomdec prints
  `ref1=0` (INTRA_FRAME => interintra) for this block where OUR `EC_MODE_VAL`
  prints `ref1=-1` (none), and our counters do report
  `rect_wedge ... interintra=[5,6,2,4,0,0]` (4 of them 32x16). Either our
  print normalises INTRA_FRAME to -1, or we are not applying interintra on
  this block at all -- resolve that before touching the convolve. A uniform
  (dither-free) offset over a whole skip block means a DC-only difference:
  an unapplied/extra interintra blend term or an offset in the 10-bit
  convolve rounding chain, NOT a filter-tap error (taps would dither).
* A hand-rolled 8-tap REGULAR prediction from the (exact) f0 reference at
  mv (-20.75, +44.25) did NOT reproduce either decoder's pixels, so the
  position/convention of that hand check was wrong -- do not trust it.
