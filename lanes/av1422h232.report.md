# lane-av1422h232 — the 4:2:0 odd-height reconstruction defect is an **IDTX/DCT_DCT chroma tx_type loss** on 32-point inter chroma

Base `9d5f7bd9` (fast-forwarded to `3f08ae3f`, tree clean, **no code change**).
Worktree `~/.cache/wt/av1422h232`, branch `lane-av1422h232`.

## Verdict

**The defect is a one-line-class bug with a decisive measurement behind it: for an
inter/intrabc block whose luma transform coded `IDTX`, our decoder resolves the
32-point CHROMA transform type to `DCT_DCT` while libaom inherits the luma's
`IDTX`.** The coefficients are byte-identical on both sides; only the transform
differs, and `IDTX` (a plain copy) versus `DCT_DCT` (a separable IDCT) produce
completely different residual shapes.

I did **not** ship the fix: the measurement localises the site, but confirming it
requires reading `reduce_inherited_chroma_tx_type` / `av1_get_ext_tx_set_type`
against each other, and a speculative edit to a bit-exact decoder on a hunch is
exactly what lane-av1422anom was chartered to avoid. The unblock is named in §7
and is one function.

The trigger is **not** a height or width rule. It is content: any stream with an
inter/intrabc block whose luma codes `IDTX` and whose chroma plane block reaches
32 points **with nonzero coefficients**. 8 of the 27 cells I swept fail; the
passing heights are not the multiples of 8 (232/236/248 fail, 240/244 pass).

## 2. Localisation

`frames=0` (the keyframe — no inter prediction, so motion compensation is
exonerated outright). The wrong region is two perfect rectangles:

| plane | chroma rows | chroma cols | count |
|---|---|---|---|
| U | 96–115 | 128–137 | 200 |
| V | 96–115 | 128–152 | 500 |

Chroma plane 160×116. So the region is rows 96–115 = **every visible row of one
block**, cols 128–152 ⊂ that block's 128–159.

`TRACE block px=256 py=192 side=64` — a single **64×64 luma block at (256,192)**
overlaps the region, chroma origin (128,96), chroma extent 32×32 clipped to 32×20
at the bottom edge. Luma is exact, so the block decomposition and the luma
transform are both right.

```
TRACE partition_w64 ctx=3 value=0
TRACE skip value=0 rng=36043
TRACE use_intrabc value=1
TRACE intrabc dv=(-1344, 0)
TRACE block px=256 py=192 side=64 mode=0 uv_mode=0
TRACE dequant plane=0 ... tx_type=Idtx side=32     <-- luma codes IDTX
TRACE dequant plane=1 ... tx_type=DctDct side=32   <-- chroma: WE say DCT_DCT
TRACE dequant plane=2 ... tx_type=DctDct side=32   <-- chroma: WE say DCT_DCT
```

It is an **Intra-Block-Copy** block (`use_intrabc=1`, `dv=(col 0, row -1344)` in
1/8-pel = −168 luma px = −84 chroma px). aomdec reads the identical symbols
(`EC_ISTEP … name=intrabc val=1 rng=49872`, `EC_DV … dv_col=0 dv_row=-1344`), so
the entropy decode of the block agrees on both sides.

### The prediction is right; the residual is not

* **Source.** DV −84 chroma rows → source chroma row 12. Our chroma prediction
  row 0 is `202 202 202 202 202 202 166 166 …`, byte-identical to our own frame 0
  row 12 (the copy source) and to the oracle's own final rows 100–115.
* **Entropy is identical.** Pairing `EC_ECDUMP_IN` on both sides:

  | side | entry |
  |---|---|
  | oracle | `plane=1 mi=(48,64) bc=0 br=0 tx=3 ECIN=(19742,34733,25032)` |
  | ours | `side=32 ctx=2 dcctx=1 ECIN=(19742,34733,25047)` |
  | oracle | `plane=2 … ECIN=(20792,37128,25058)` |
  | ours | `side=32 ctx=2 dcctx=1 ECIN=(20792,37128,25073)` |

  (our `ctx=2` vs the oracle's `ctx=9` is our table's baked-in `+7` chroma
  offset, per `read_plane`'s own comment — same logical context, not a
  difference. The `bit` counter's +15 is a different convention.) The msac state
  entering **and leaving** each chroma unit matches exactly, and aomdec's
  `EC_COEFF_VAL plane=1 row=0 col=0 rng=37128` equals our next unit's range 37128.
* **The coefficients are identical.** aomdec's `EC_DQCOEFF` rung for this unit:

  ```
  EC_DQCOEFF plane=1 w=32 h=32 0:-105 32:-80 64:-60 96:-40
  EC_DQCOEFF plane=1 txsize=3 txtype=9 eob=7 nz=0:-105,32:-80,64:-60,96:-40,
  ```

  Our quantized levels are `[-6, -4, -3, -2, 0, …]` at the same four positions,
  `eob=7` both sides. `post_golomb c=0 level=6 / c=1 level=4 / c=5 level=3 /
  c=6 level=2` on aomdec's side is the same sequence.
* **`txtype=9` is `IDTX`.** libaom's `TX_TYPE` enum has `IDTX = 9`. With an
  identity transform the residual is a direct copy, and the oracle's row 96
  residual is exactly the dequantized coefficients shifted by the 8-bit inverse
  transform's final `>>2`: `−105>>2 = −26`, `−80>>2 = −20`, `−60>>2 = −15`,
  `−40>>2 = −10` — which is precisely the observed oracle row 96
  `176 182 187 192 202 202 …` against a `202 202 202 202 …` prediction.
  Our `DCT_DCT` instead produces a 32-point separable IDCT of that input: flat
  down the rows, `−3 −3 −3 −2 −2 −2 −2 −1 …` across row 0, which is exactly our
  output `199 199 199 200 200 200 164 165 …`.

### Why the filters are still exonerated

The prior lane's PREFILT/deblock/CDEF/LR ladder compared **our PREFILT against
the oracle's FINAL**, which is not the right pairing (it cannot separate
"reconstruction differs" from "the filters then changed it"). The correct
statement, and the one this lane measured, is simpler: the wrong samples are a
**keyframe** block's reconstruction and every filter stage is a pure function of
reconstruction, so nothing downstream can produce a difference that is not
already in reconstruction. That holds regardless of the PREFILT pairing, and the
`txtype` measurement above pins the cause to reconstruction with no filter
involved.

**The trigger rule is not geometric.** 232, 236 and 248 fail while 240, 244, 252
and 256 pass; 232 and 248 are multiples of 8 and so are 240 and 244. The real
rule is content-dependent: *an inter/intrabc block whose luma codes `IDTX` and
whose chroma plane block reaches 32 points with a nonzero coefficient*. Cells
whose content never produces that shape are exact.

Every failing cell shows the same fingerprint. Nonzero 32-point chroma
`EC_DQCOEFF` on the failing cells:

```
o320x248 : EC_DQCOEFF plane=1 txsize=3 txtype=9 eob=40 nz=0:-224,1:-222,2:-203,3:-129,4:-222,5:-111,32:-277,…
o322x232 : EC_DQCOEFF plane=1 txsize=3 txtype=9 eob=15 nz=0:-128,32:-92,64:-55,96:-55,128:-18,
o324x240 : EC_DQCOEFF plane=1 txsize=3 txtype=9 eob=31 nz=0:-216,1:-143,2:-123,32:-164,33:-225,…
```

**`txtype=9` (IDTX) on every one of them.** The contiguous `0,1,2,…,5,32,33,…`
index pattern is itself the signature of an identity transform.

`320x236` additionally has 234 349 wrong **luma** samples with
`Y=234349` — a second, larger defect (236 is not a multiple of 8, so its luma
plane overhangs the coding grid). **That is a different class and this report
does not claim it is the same mechanism**; see `not_done`.

### Is 4:2:2 the same mechanism?

**Almost certainly yes, and it is why the 4:2:2 cells in the prior lane's table
(`S_422_320x242`, `R_422_324x242`, `X_422_320x232`, `X_422_320x248`,
`O_odd322x242`) all diverge.** The mechanism is in the chroma transform-type
resolution for an inter block, which is shared by every chroma format — it is
keyed on `plane > 0` and on the block being `is_inter_block`, not on
subsampling. The one exception is the odd-width `2 * ceil(w/8)` vs `ceil(w/4)`
mi-grid skew, which is a *separate* bug and is only reachable at odd widths, so
it is a separate finding, not part of this one.

## 6. Non-vacuity proofs

* **Comparator:** one flipped byte in the real `aomdec --rawvideo` buffer moves
  the reported wrong count by exactly +1 in the right plane and frame (§1).
  Four runs, four distinct planes/frames.
* **Pin reproducibility:** an independent re-encode of the same recipe produced
  the same sha256 as the committed fixture.
* **Mechanism, not inference:** the `txtype` difference is measured on both
  sides for the same unit (`EC_DQCOEFF … txtype=9` vs our `tx_type=DctDct`) with
  identical coefficients, identical eob, and identical msac state in and out.

## 7. `not_done` — and the exact unblock

- **No fix shipped.** The remaining work is inside the chroma transform-type
  resolution for an inter block at 32 points:
  * `crates/ec-av1/src/decode.rs`, `read_plane`'s `default_tx_type`
    (`if plane_idx == 0 || side >= 32 { TxType::DctDct }`) — that `side >= 32`
    arm is our `EXT_TX_SET_DCTONLY` clamp. It fires here and drops the luma's
    inherited `IDTX`.
  * the inter twin `read_inter_plane`'s `reduce_inherited_chroma_tx_type(t, side, side, fctx)`.
  * against libaom `av1_get_tx_type(…, PLANE_TYPE_UV, …)` +
    `get_ext_tx_set_type` in `blockd.h`, which is what produced `txtype=9`.

  **Deciding measurement still owed:** whether libaom's
