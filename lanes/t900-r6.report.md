## STEP 2 -- frame 14's U-only residue: LOCALISED, NOT FIXED

Re-measured on this tip with the 16-frame cut `~/.cache/t900-tmp/t900_h.obu`
(the 14-frame witness stops one frame short of it): decode-order frames 0..13
exact, frame 14 = 32 differing bytes, frame 15 = 28.

Prefilter compare (`pf.sh`, `~/.cache/t900-tmp/pf_h2/`) narrows it much further
than r5's post-filter numbers:

* frame 14: **Y 0, V 0, U 14 pixels**, bbox chroma x 472..475, y 284..287 --
  exactly ONE 4x4 chroma transform unit, aligned.
* frame 15: same superblock, U 24 pixels, bbox x 472..477 y 281..288.

That unit is the chroma of the 8x8 inter block at luma (944,568) = mi(142,236),
which our `EC_TRACE_MODE` shows as an INTER COMPOUND leaf (`cmode=24 ref0=1
ref1=5`), NOT an intra-in-inter block -- r5's handoff premise ("intra-in-inter
8x8, CfL alpha or chroma DC suspected") is DISPROVED twice over: `EC_PRED` emits
no intra prediction at that chroma position at all (only at y=288), so CfL
cannot be involved.

What the shape of the residue rules in and out:

* V is exact and comes AFTER U in the same block, and no later block differs --
  the entropy stream is in sync. So this is reconstruction, not a symbol.
* Y is exact, so it is not the block's motion vectors, its compound mask or its
  reference; chroma MC is plane-symmetric and would move V too.
* The 4x4 diff is a smooth low-order-AC pattern (+4..+8 top-right, -7..-5
  bottom-left, see the block dump in the handoff), i.e. one or two AC
  coefficients' worth of basis, exactly the signature of an inverse transform
  fed the right coefficients with the WRONG basis -- class
  `tx-type-set-membership` (an inter chroma unit inherits the colocated luma
  `tx_type`; a wrong choice inside the same TX_CLASS leaves the msac range
  untouched and corrupts only the pixels).

`reduce_inherited_chroma_tx_type` (decode.rs:14794) and `read_inter_luma8`'s
top-left-unit rule (decode.rs:14700) were both read and both look right for
this shape, so the next step is the oracle rung, not another code read: the
aom oracle prints `EC_COEFF_STEP tag=tx_type plane=%d` with NO value
(decodetxb.c:182) -- printing `tx_type` there and diffing that one line for
this TU decides it in one run.

Disposition: deferred(the oracle's `tag=tx_type` line needs the VALUE printed
and aomdec rebuilt) -- everything else about the defect is pinned above.
