## A -- intrabc (re-verified, nothing left to do)

`$HOME/.cache/kf900-r5/b.obu` decodes PIXEL-EXACT against ffmpeg with `976958b` in place
(cmp of the whole 73728-byte frame). Root cause of that commit, restated with its libaom
line: `av1_get_tx_type` (`av1/common/blockd.h`) branches `PLANE_TYPE_UV` on
`is_inter_block(mbmi)`, and `is_inter_block` counts `is_intrabc_block` (`blockd.h:373`),
so an intrabc block's chroma `tx_type` is the colocated LUMA transform's coded type, not
`intra_mode_to_tx_type` of the chroma mode. We read `DCT_DCT` (TX_CLASS_2D) where libaom
had `V_DCT` (TX_CLASS_VERT), which moves `eob_multi_ctx`, the scan and every nz context.
The chartered DV premise was stale and is disproven in that commit's message (oracle
`EC_TRACE_IBC` at `decodemv.c:752`: `dv=(-512,-608)` on both sides).

The intrabc GATE the charter asked for already exists and is green:
`a_real_aomenc_screen_key_frame_reads_use_intrabc_on_rect_strips` -- 7 arms,
`--tune-content=screen --enable-intrabc=1`, per-arm `rect_intrabc_reads` +
`intrabc_hits` counters, every frame of every decoding arm compared,
`out_of_scope_mismatch == 0`. `gate_coverage` no longer lists `enable-intrabc` as a
never-exercised tool at EITHER depth (8-bit dropped by `976958b`, 10-bit dropped here).

No intrabc refusal was lifted: rect-strip intrabc reconstruction still fires by name in
arm 0 (and in `DIFF_45_1_1_test.obu` below), so the inventory stays at 47.
`deferred: rect-strip intrabc reconstruction -- unblocked by porting BILINEAR prediction
from the pre-filter current frame at rect shapes; today the gate proves the refusal fires
rather than being silently wrong.`

## B -- the palette defect, fixed (root cause + libaom line)

libaom keeps `palette_size` / `palette_colors` per 4x4 mi cell in `MB_MODE_INFO`, and
`av1_get_palette_cache` (`pred_common.c:73`) / `av1_get_palette_mode_ctx`
(`pred_common.h:197`) read `xd->above_mbmi` / `xd->left_mbmi` -- the mi cell immediately
above/left of the block. Our eight `Neighbours::{above,left}_palette_*` arrays held ONE
entry per 16px `SUB` cell. That corner-cut's own comment said it was "safe today because
every sub-16 leaf path refuses palette outright"; lane-kf900 r4 lifted exactly those
refusals, so it stopped being true. A 32x8 / 16x8 strip pair sits inside one cell, and
strip 1's neighbour lookup returned a sibling's palette: for mi(0,8) libaom reads mi(0,7)
(the 16x8 block at mi(0,4), palette size 3) while our slot had been overwritten by
mi(2,4) (size 2), so `read_palette_colors_y`'s cache-hit branch narrowed a different
interval and the tile desynced there.

The charter's ORDER question is answered and is NOT the defect: `parse_decode_block`
(`av1/decoder/decodeframe.c:1158`, `:1176`) calls `av1_visit_palette(...,
av1_decode_palette_tokens)` before `read_tx_size`, and our rect reader already has that
order.

Changes (all `crates/ec-av1/src/decode.rs` unless noted):

| path | why |
| --- | --- |
| `Neighbours::new` palette arrays | sized `cols * (SUB / MI)` / `rows * (SUB / MI)` -- mi granularity, libaom's own |
| `record_palette_y_rect` / `record_palette_uv_rect` | take the block's REAL mi position, stamp `(w / MI).max(1)` x `(h / MI).max(1)` cells, bounds-guarded |
| `record_palette_y` / `record_palette_uv` | SUB-taking wrappers convert, so every SUB-aligned call site is untouched |
| `palette_ctx_and_cache_mi` / `palette_uv_cache_mi` | one mi coordinate instead of `(SUB cell, mi_row)`; `left_ok` compares against `tile_col0_mi` in mi units |
| `record_strip_palette` | mi position, writes BOTH axes over its own span; the `last` split-axis hack (and the two `pal_last` computations feeding it) is deleted -- it only existed because all four 1:4 strips aliased onto one SUB slot |
| call sites: rect (`(mi_r, mi_c)`), rect leaf (`leaf_mi`), rect4-32 (`(mi_r, mi_c)`), rect4-16 (`lmi`), sub8 non-palette clears (`leaf_mi`) | each passes its real mi position |
| `crates/ec-av1/src/stream.rs` | palette gate arms 3-4 |
| `crates/ec-av1/src/gate_coverage.rs` | `enable-intrabc` leaves the 10-bit never-exercised list |
