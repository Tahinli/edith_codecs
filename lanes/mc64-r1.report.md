# lane-mc64 r1 — RED (charter premise disproved; real defect re-localised)

## Verdict
RED. The charter's defect description is wrong in its central fact: the
mismatching block is **not** an inter NEWMV block off GOLDEN with a half-pel
mv. It is a **64x64 INTRA block inside an inter frame** (no motion
compensation happens for it in either decoder), so every one of the charter's
six candidate causes (a)..(f) is about a code path this block never enters.
No fix shipped; the lane is re-pointed, with the measurement chain below.

## ROOT LOCALISATION — the block is intra, not inter
1. `aomdec EC_TRACE=1 EC_TRACE_MODE=1` interleaved: the frame-2 superblock at
   mi(16,32) reads `EC_PART_VAL mi_row=16 mi_col=32 bsize=12 value=0`
   (PARTITION_NONE, 64x64) and then **no `EC_MODE` and no `EC_IMODE` line at
   all** — the next trace line is the following frame's first `EC_PART`
   (`tell=1`).
2. Oracle source, `av1/decoder/decodemv.c:1698-1710`: `read_inter_frame_mode_info`
   prints `EC_MODE` only from `read_inter_block_mode_info`; the
   `read_intra_block_mode_info` arm (intra block in an inter frame) is
   **uninstrumented**. Silence there means `inter_block == 0`, not "no block".
3. Our decoder agrees: `EC_MODE mi_row=16 mi_col=32 is_inter=0 skip=false`
   with `EC_IB px=128 py=64 side=64 w=64 h=64`, and **zero** MC / warp /
   compound calls for it (`EC_MC_TRACE` instruments `mc::predict_with_filters`,
   `mc::predict_compound_intermediate` and `warp::warp_affine`; 33 MC calls in
   the whole decode, none at this block).
4. The charter's `mode=16 ref0=4 mv0=(-340,-116)` line is real but belongs to
   **decode-order frame 1**, where mi(16,32) is `EC_PART_VAL bsize=12 value=3`
   (SPLIT) into four 32x32 blocks. Frame 1 is pixel-exact for us. This is the
   class `[[dump-not-call-unique]]` / `[[stale-output-faked-measurement]]`
   again: a coordinate-keyed grep with no frame key picked the wrong call.

EVIDENCE: ~/.cache/mc64-tmp/{aom_both.log,aom_part.log,mct4.log} | aomdec EC_TRACE+EC_TRACE_MODE and our EC_MC_TRACE on the pinned obu | frame-2 mi(16,32) = PARTITION_NONE 64x64 with no mode trace line; ours is_inter=0, 0 MC calls; frame-1 mi(16,32) = PARTITION_SPLIT, that is where mv=(-340,-116) lives

## What the defect actually is (direction, not yet a fix)
A 64x64 **intra** block in an inter frame: luma wrong by -12..+9 over 3720 of
4096 samples, chroma (32x32, TX_32X32) bit-exact. Luma is the only plane with a
64-length transform, and `av1_get_adjusted_tx_size` codes only the top-left
32x32 of a TX_64X64. So the suspects are, in order: the TX_64X64 coefficient
region / eob domain, the 64-point inverse transform's row/col zeroing, and the
intra prediction of a 64x64 block. The error is structured, not a constant
offset, which argues residual over prediction — 376 of 4096 samples are equal,
so it is not a wholesale desync either.

## What changed
* `crates/ec-av1/src/decode.rs` — `stage_dump_idx()`; `dump_stage`/`dump_stage16`
  now key their file on the decode-order picture index instead of always
  writing `.f0`. Before this, `EC_AV1_POSTDEBLOCK_DUMP`/`POSTCDEF_DUMP` compared
  the LAST decoded frame no matter which frame you meant (the ledger records
  this for the pre-8c6065e prefilt dump; the postdeblock/postcdef twins were
  never fixed). This is a real instrument defect, fixed, not a workaround.
* `crates/ec-av1/src/decode.rs` — `EC_MC_TRACE` prints `EC_IB px py side w h`
  at `decode_inter_block` entry; `EC_MODE` now carries `is_inter=` and `skip=`.
* `crates/ec-av1/src/mc.rs`, `crates/ec-av1/src/warp.rs` — `EC_MC_TRACE` prints
  `EC_MC_CALL` / `EC_MC_COMP` / `EC_MC_WARP` with the q4 position, block size,
  subpel fractions and resolved kernels. Placed BEFORE the whole-pel fast path
  so a block that takes no MC call at all is visible as an absence.
* `crates/ec-av1/fixtures/av1_192x128_8bit_intra64_in_inter.obu` — the stream,
  pinned (`git add -f`), because its recipe does not reproduce it.
