## What changed

- `crates/ec-av1/src/decode.rs`
  - `SCAN_32X8` / `SCAN_8X32` (new, ~line 1650): row-major transcriptions of
    libaom `default_scan_32x8` / `default_scan_8x32`, converted with
    `row*w+col = (p % h)*w + (p / h)` from libaom's COLUMN-major `p`. The rule
    was validated by reproducing this repo's existing `SCAN_16X8` byte for byte
    from `default_scan_16x8` before generating anything new — and libaom's
    `default_scan_16x8` literal is byte-identical to this repo's `SCAN_8X16`,
    i.e. a naive copy installs the transpose (class
    reference-layout-not-spec).
  - `decode_block_rect64`: luma corner generalised from a hardcoded 32x32 to
    `(bw.min(32), bh.min(32))`, reading 32x16/16x32 through `read_coeffs_rect`
    with `SCAN_32X16`/`SCAN_16X32` and `TxbSet::LumaRect32x16`; chroma set/scan
    picked per shape, 32x8/8x32 reading `TxbSet::Chroma16` with the new scans.
    Why no new CDF tables are owed, all read out of the oracle source:
    `av1_get_adjusted_tx_size` maps TX_64X16→TX_32X16, TX_16X64→TX_16X32
    (`blockd.h:1361`); `av1_scan_orders` gives TX_64X16 `default_scan_32x16`
    ("tx32's scan order is used", `scan.c`); `get_txsize_entropy_ctx` is 3 for
    both TX_64X16 and TX_32X16 and 2 for both TX_32X8 and TX_16X16;
    `txsize_log2_minus4` is 5 for TX_64X16 *and* TX_32X16, 4 for TX_32X8 *and*
    TX_16X16 (`common_data.h:346`) so the eob alphabet matches too; and
    `av1_nz_map_ctx_offset[TX_64X16]` is literally
    `av1_nz_map_ctx_offset_32x16` (`txb_common.c:340`) — which is what
    `base_ctx_rect(32,16)` computes, since both raw and coded dims are w>h.
  - `PARTITION_HORZ_4`/`PARTITION_VERT_4` (8/9) wired at the superblock level:
    four strips, `quarter_step` = 1 SUB unit, with libaom's `i > 0` frame-edge
    break.
  - New per-orientation hit counters `sb_rect4_horz_hits()` /
    `sb_rect4_vert_hits()`.
- `crates/ec-av1/src/refusal_inventory.rs`: SB-level string narrowed to
  "a superblock-level HORZ_A/HORZ_B/VERT_A/VERT_B partition (… codes NONE,
  SPLIT, HORZ, VERT and the 1:4 pair at 64x64)".
- `crates/ec-av1/src/stream.rs`: new gate
  `a_real_aomenc_stream_with_a_superblock_level_1to4_partition_decodes_pixel_exact`.
- `crates/ec-av1/fixtures/tx64x16-vert4-mismatch-seed73.obu`: the failing
  stream, pinned.

## Gate

`cargo test -p ec-av1 --lib -- --exact stream::tests::a_real_aomenc_stream_with_a_superblock_level_1to4_partition_decodes_pixel_exact`
(`EC_TX64X16_GATE_ATTEMPTS`, default 40). aomenc recipe = the sbpart gate's,
with `--enable-1to4-partitions=1` and `--min-partition-size=16`; odd attempts
render the generator rotated 90 degrees (`transpose=1`) because aomenc picks
VERT_4 on this content and essentially never HORZ_4, and the two arms are a
transposed pair. Attempts whose decode fired zero 1:4 strips are counted and
printed, never asserted on — selection is on "the stream contains the
feature", never on "the stream decoded correctly".

RESULT: **FAIL**. `seed 73` (a stream with four real 16x64 `PARTITION_VERT_4`
strips at mi(16,16..28)) mismatches ffmpeg: 10754 wrong luma samples, first at
(64, 56) — one row band ABOVE the strips, i.e. across the y=64 deblock edge.
An earlier 13-attempt run (before the transpose arm) had VERT_4 fire 4 strips
and decode PIXEL-EXACT, so the skip/low-energy case works and the coded case
does not.
