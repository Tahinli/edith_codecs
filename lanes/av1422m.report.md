# lane-av1-422m — the (4, 32) refusal is replaced by libaom's TX_4X4 chunking for
# that one shape; the header refusal STAYS (the stream's next stop is a
# different class, the intra-in-inter 64x64 chroma (32, 64) panic)

## Outcome

1. `read_inter_rect_chroma` no longer refuses (4, 32): an 8x32 luma block's
   4:2:2 chroma plane now codes as EIGHT TX_4X4 chunks per plane, exactly the
   chunking libaom's decoder performs for a plane whose `ss_size_lookup` entry
   is BLOCK_INVALID. 4:2:0 and 4:4:4 are bit-identical by construction (the
   arm gates on ss (1,0) AND write rect exactly (4, 32) — impossible at any
   other format).
2. The header refusal is NOT deleted: with the chunking in, the 16-frame
   stream decodes PAST the previously refusing block and stops at a NEW hole
   owned by another lane — the intra-in-inter 64x64 chroma arm reads its whole
   (32, 64) plane as ONE unit and trips the rect-coeff scratch bound. The
   delete condition (16-frame pixel-exact vs aomdec) is unmet, so the refusal
   stays.

## The chunking mechanism (measured against the pinned oracle, `~/.cache/aom-oracle/src`)

- `av1_ss_size_lookup[BLOCK_8X32][1][0] = BLOCK_INVALID`
  (`av1/common/common_data.c:38`): an 8x32 luma block HAS no 4:2:2 plane
  residual block; no TX_4X32 exists either.
- `decode_token_recon_block`'s inter residual loop
  (`av1/decoder/decodeframe.c:1022`) still walks the plane in
  `get_vartx_max_txsize` units. `get_vartx_max_txsize`
  (`av1/common/blockd.h:1447`) does `max_txsize_rect_lookup[plane_bsize]`
  with `plane_bsize == BLOCK_INVALID` — one element PAST the 22-entry table.
  The oracle build is Release (`CMakeCache.txt`: `CMAKE_BUILD_TYPE=Release`,
  asserts compiled out), and the table's adjacent neighbour in declaration
  order is `vtx_tab`, whose first entry `DCT_1D = 0 = TX_4X4`. So the
  chroma max tx size resolves to TX_4X4.
- `decode_reconstruct_tx` (`decodeframe.c:303`) NEVER recurses for chroma
  (`if (tx_size == plane_tx_size || plane)`), so every chroma unit reads at
  TX_4X4: the 4x32 plane codes as 8 stacked 4x4 coefficient units.
- Empirical proof the chunking matches the bitstream: the same fixture bytes
  (sha256 `d3fa4beeb1309033e4a03f5ae5c431c8fa8386ba1ada088684710423c7938129`)
  stopped at the (4, 32) refusal before the change; after it, decode consumes
  that block's chroma and reaches the LATER intra-arm panic below — entropy
  stayed consistent across the chunked units.

## The fix (scoped to the one shape)

`read_inter_rect_chroma` (`decode.rs`): when ss is (1, 0) and the write rect
is exactly (4, 32), chunk into (4, 4) units — the existing multi-unit loop
then stamps per-unit chroma neighbour contexts, embeds into the square-stride
grid, and returns the per-unit list for the tail's re-stamp, unchanged. Each
unit reads `TxbSet::Chroma4` / `default_scan(4)` (the lane-av1-422j rows) and
inherits NO tx_type (`av1_get_tx_type` returns DCT_DCT for
`tx_size == TX_4X4`, blockd.h), so `inherit_tx_type` is `None` for these
units.

Counter `CHROMA422_CHUNK_HITS` (+ `chroma422_chunk_hits()`, printed by
`decode_probe` as `chroma422_chunk:`): one hit per TX_4X4 chunk unit read; a
4:2:0/4:4:4 frame cannot increment it. On the current fixture the probe
panics at the later stop before `report()` prints, so the number is not yet
exercised on a full decode; the units demonstrably ran (frontier evidence
above).
