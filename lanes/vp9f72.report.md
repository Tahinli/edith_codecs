## Root cause

**The entropy-context write-back of a transform block applied the frame-edge
shift to a 64-bit spread, so it zeroed bytes BEYOND the window instead of the
window's tail.**

libvpx `vp9_detokenize.c:273-323` (`vp9_decode_block_tokens`) writes:

    case TX_8X8:
      get_ctx_shift(xd, &ctx_shift_a, &ctx_shift_l, x, y, 1 << TX_8X8);
      ...
      *(uint16_t *)a = ((eob > 0) * 0x0101) >> ctx_shift_a;
      *(uint16_t *)l = ((eob > 0) * 0x0101) >> ctx_shift_l;

The shift is applied to a value **whose width is the written window's** (u16
for `TX_8X8`, u32 for `TX_16X16`, u64 for `TX_32X32`), so `>> 8` on a two-byte
window yields `0x0001` — bytes `[1, 0]`. Our port shifted the full 64-bit
spread (`0x0101..01 >> 8` = `0x0001_0101_0101_0101`) and then took byte `k`,
which leaves bytes `[1, 1]`: the window's last slot keeps its old value.

`get_ctx_shift` only fires when the block runs past an edge
(`xd->max_blocks_wide/high != 0`, i.e. `mb_to_*_edge < 0`), which needs an mi
extent that is not a multiple of the block size — for 1080 (mi_rows 135) that
is exactly the **last, partial superblock row**. So frames 0..~71 behave and
the defect shows up wherever a bottom-row chroma block's stale tail slot is
later read as an entropy context.

Mechanism as an equation (the written window for `nblocks` slots):

| | written bytes |
|---|---|
| libvpx | `mask(nblocks) >> shift` |
| our port (bug) | `(mask(8) >> shift)` truncated to `nblocks` bytes |

`mask(n) = (eob>0) * 0x0101..01` over `n` bytes. The two agree only for
`shift == 0` (every other corpus stream, every non-edge block) — hence a
corpus-only defect.

### The two-site oracle that pinned it

A **fresh** instrumented libvpx 1.15.0 was built for this lane (the parse-time
`/tmp/vp9loss` build was gone; `$HOME/.cache/vp9pix/drv_pix` is a static
pixel-only driver and could not print contexts). Build + instruments:

    $HOME/.cache/vp9f72/libvpx-1.15.0                     # configure --disable-unit-tests --disable-vp8
                                                          # --disable-vp9-encoder --disable-examples --disable-tools --enable-pic
    vp9/decoder/vp9_decodeframe.c : g_dbg_row/g_dbg_col/g_dbg_bsize set in decode_block;
                                    `SKIPCTX` print at the end of dec_reset_skip_context
    vp9/decoder/vp9_detokenize.c  : `TXBW`  print of (row, col, plane, x, y, tx, a[], l[]) before the switch;
                                    `TXBWC` print of (ctx, eob, shift_a, shift_l, written a[]/l[]) after it
    $HOME/.cache/vp9f72/drv_txbw                          # drv.c linked against that build

Per-frame arming without rebuilding the driver: `$HOME/.cache/vp9f72/armtrace.c`
is an `LD_PRELOAD` that counts IVF header/size reads (`fread`) and sets/unsets
the instrument env vars at the requested frame (`TRACEFROM=72 TRACETO=73
ARMVARS="TXBW=1 SKIPCTX=1 MODEDUMP=1"`). Both sides' events are then compared
block by block.

**First divergent event (pre-fix), tile 3, decode-order index 2076:**

    O  (132,180) plane 1 bcol=2 brow=2 tx=1 eob=3 sl=8  lw=[1, 0]
    M  (132,180) plane 1 bcol=2 brow=2 tx=1 eob=3 sl=8  lw=[1, 1]

Same shift (`sl=8`), different written window — the bug above, exactly.

**First divergence that reads it** (same tile, block `(132,200)`):

    O (132,200) p=1 bcol=0 brow=2 tx=1  a=[0, 0] l=[0, 0]  ctx=0
    M (132,200) p=1 bcol=0 brow=2 tx=1  a=[0, 0] l=[0, 1]  cin=1

and in the bool trace the first differing read is the first coefficient bool
of that transform block: oracle prob **217** (band 0, ctx 0), ours prob **98**
(band 0, ctx 1) — the "same ordinal, different question" signature of a wrong
entropy context, 3 bools after the tile's marker read.

## Fix

One rule, one place: `write_tx_context` (`crates/ec-vp9/src/decode.rs`) now
mirrors libvpx's per-tx-size casts — narrow the spread to the window width
FIRST, then apply the edge shift:

    let narrow = 64 - 8 * nblocks;                       // libvpx's cast
    let spread_a = ((eob_pos * ONES) >> narrow) >> shift_a.min(8 * nblocks);
    let spread_l = ((eob_pos * ONES) >> narrow) >> shift_l.min(8 * nblocks);

The `.min(8 * nblocks)` clamp is the only liberty taken: libvpx shifts a wider
type by more than its own width there (undefined in C, 0 on x86); the clamp
makes the same intent total in Rust. It is unreachable from the walk (a block
entirely past the edge is never visited).

Both call sites use it: the inter token path (`decode_inter_tx_tokens`) and
the intra-in-inter path (`predict_and_reconstruct`). The latter already had
per-width casts and was correct — sharing the helper keeps the class fixed in
one place instead of two.

## Deferred / limitations (explicit)

- **The horizontal half of the class has no witness.** `shift_a` follows the
  same rule and uses the same helper, but `mb_to_right_edge < 0` needs an mi
  extent that is not a multiple of the block size in the COLUMN direction
  (mi_cols odd), which no corpus stream here reaches — a 1918x1080 stream
  (`mi_cols` 240, even) decodes 120/120 identically on BOTH the base and the
  fixed trees, so it is not a witness. `deferred(<no reachable width in the
  corpus>)`: the vertical half is what real content hits.
- **Cross-lane scope**: the odd-*coded*-extent path belongs to `lane-vp9-odd`
  (merged on main as `e8152b9b`, which does not touch the write-back). My fix
  is orthogonal — verified inert: `odd.ivf` decodes byte-identically on the
  base and this lane (460800 bytes, `cmp` equal). The odd-dims refusal is left
  in place.
- Diagnostics kept (gated by the existing scratch hook `EC_VP9_TOKDGB`):
  `TDB` (transform-block context read, pre-existing), `TDW` (write value +
  shift + written window, both token paths) and `TDK` (skip-context reset).
  They are the instruments that isolated this defect; a next context lane can
  re-derive any of the tables above from them.
