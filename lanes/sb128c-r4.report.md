## (1) The x=64 band -- ROOT CAUSE FOUND AND FIXED

Method: stage bisection with the aomdec instrumentation rungs, decode order.

| decode-order frame | pre-filter | post-deblock | final (CDEF+LR) |
|---|---|---|---|
| 0..3 | exact | exact | exact |
| 4 | **exact** | **98 Y px, 274 C** | 98 Y / 274 C |
| 5..8 | wrong | wrong | wrong |

Pre-filter exact + post-deblock wrong on the SAME frame => the loop filter, not
a symbol. The decisive measurement: against `EC_AV1_PREFILT_DUMP`, aomdec's own
post-deblock dump changes **ZERO** pixels in luma columns 50..78 of that frame,
while ours changes 98 (peak 26 at column 63, footprint 58..66 = the 14-tap
vertical filter at x=64). libaom does not filter that edge at all.

Why: libaom `av1_loopfilter.c:set_one_param_for_line_luma` (and `_chroma`)

```c
const int32_t pu_edge = mi_prev != mbmi;
if (!pu_edge) curr_skipped = mbmi->skip_txfm && is_inter_block(mbmi);
if ((pu_edge || !curr_skipped) && level) { params->filter_length = ...; }
```

`get_transform_size` still reports TX_64X64 for a SKIP 128x128 inter block, so
the transform-unit edge at x=64 exists -- it is simply suppressed because it is
not a prediction-unit edge and the block is skipped. Every 128 block in this
stream is `is_inter=1 skip=1`.

Fix (`crates/ec-av1/src/decode.rs`, commit `6226c27`):
- the per-leaf `fill_lf_grid_rect` loop (the var-tx leaf publication, ~line
  19256) is gated on `!(skip && is_inter)`. The block-level publication of
  `write_w = 128` stays, which IS the suppression. The 128 root is the only
  block that reaches that loop skipped: `read_block_tx_size`'s
  `TX_MODE_LARGEST` branch hands back four TX_64X64 leaves for `side > 64`
  regardless of `skip`, while every `side <= 64` skip inter block gets `None`.
- `fill_lf_grid_rect`'s uv extent (~line 4186) drops its `.min(32)` cap. The
  cap was INERT for every block up to 64 wide (`64/2 == 32`) and wrong for a
  128-sided one, where it published an internal chroma TU edge every 32 chroma
  px. A non-skip 128 block still gets uv 32, through its own per-leaf calls
  (`w_mi * MI == 64`).
- `dump_stage` now indexes its file per decode-order picture. It wrote a fixed
  `.f0` every frame, so `EC_AV1_POSTDEBLOCK_DUMP` only ever held the LAST
  picture and could not be compared against aomdec's indexed rung -- that is
  the instrument this root cause needed.

Result on `$HOME/.cache/sb128c-work/g-61-8-0.obu`: decode-order frames 0..4 are
now exact at pre-filter, post-deblock AND final (`EC_AV1_FINAL_DUMP`, hidden
frames included). Before the fix frame 4 was wrong at post-deblock.

## (1b) CDEF for a 128 root -- the charter's suspicion is WRONG, verified

`read_cdef` (`av1/decoder/decodemv.c`) reads at most one literal PER CALL, and
is called once per BLOCK. For a `PARTITION_NONE` 128 root there is exactly one
block in the superblock, so exactly ONE `cdef_idx` symbol is read
(`index = cdef_unit_col_in_sb + 2 * cdef_unit_row_in_sb` = 0), and it is stored
into the block's own `MB_MODE_INFO`, which every mi cell of all four 64x64 CDEF
units points at. r1's "replicated over 4 quadrants" is CORRECT; no change made.
(Four symbols are read only when the 128 root SPLITs into four non-skip 64s.)
