# lane fuzzre-b: 1 CPU-hour clean fuzz runs on the final tree (ec-h265, ec-vorbis)

Goal: DONE.md gate G2 wants one clean 1 CPU-hour run per parse/decode fuzz target. The earlier 1 h runs of these
targets predate later decoder merges, so they are re-run here on the current tree.

- Base: `main` at `f3e6c7fa`. Tree hash (`HEAD^{tree}`): `0d9662461b41b5026e7da91d652ab16e1789eae2`.
- Source changes in this lane: none. No crash was found, so nothing was fixed and no regression test was added.
- Host: b only (`user@host-b`, 4 cores). Cargo-fuzz 0.13.2 with nightly, no libva link issue for these crates.
- Command per target: `cargo +nightly fuzz run <t> -- -max_total_time=3600 -rss_limit_mb=1536 -timeout=30`.
- Seeds: `ec-h265` `seeds/*.bin` (4 files, 64x64 H.265 streams, copied into `fuzz/corpus/<t>`). `ec-vorbis`
  corpus generated by `fuzz/seed.sh` from the repo fixtures (65 seeds: 31 setup, 31 decode, plus the decode and setup
  dirs). The corpora are gitignored and were not committed.
- Logs on b: `~/tmp/fuzzre-b/<t>.log` (full run) and `~/tmp/fuzzre-b/<t>.topup.log` (top-up). Each log ends with an
  `EXIT <code>` line. Queue driver: `~/tmp/fuzzre-b/drive.sh`, top-up: `~/tmp/fuzzre-b/topup.sh`.

## Schedule

The two ec-h265 targets ran first. The two ec-vorbis targets started when the first ec-h265 run finished, per the
ordering in the charter. So at most three fuzzers ran at once, and the first hour ran two at a time.

## Results

Wall seconds come from libFuzzer's `Done N runs in S second(s)` line. CPU seconds were sampled with `ps -o cputime`
during each run. libFuzzer is single-process, so CPU tracked wall closely. Samples at elapsed ~3360 s showed CPU
about 27 s behind wall, so each run's final CPU is estimated at about 3570 s. The top-up below closes that gap.

The top-up columns are 120 s resumes from each target's grown corpus, run with the same binary. The "Total wall s"
column is full run plus top-up (3601 + 121). The "Total CPU s" column is the estimate described above.

Crashes: 0 in all four targets. `artifacts/` directories are empty for all four. Each `grep` for `ERROR: libFuzzer`,
`panicked` and `deadly signal` returned 0 hits in the vorbis logs.

Coverage sanity: each ec-h265 target has a 64-pixel size cap, and the seeds are 64x64 streams. The corpora grew
(decode_annexb to 3,632 entries, parse_params_slice to 3,149 entries), so the seeds pass the caps. The vorbis decode
target caps the input at 4096 bytes, and its corpus grew to 261 entries. Coverage plateaus at 1556 to 1684 for the
parse-only and vorbis targets, well above the 722 that was rejected for server a's AV1 run. The high exec/s on
parse_params_slice (about 2,700) and vorbis setup (about 450) is consistent with parse-only targets.
