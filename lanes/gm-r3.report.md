## Root cause

Hand-verified our `gm_get_motion_vector` (`warp.rs`) against the real oracle's `mv.h:183-286` (`~/.cache/aom-oracle/src/av1/common/mv.h`, foreign implementation, not our own transcription): found and fixed a genuine bug -- `block_center_x`/`block_center_y` (mv.h:183-191) subtract 1 from the halved-block-size offset (`mi_col*MI_SIZE + bw/2 - 1`); our `warp.rs` was missing the `- 1` on both axes. Fixed in `warp.rs`. This is a real spec-conformance bug (kept fixed) but hand-computing both versions for this exact block showed the `-1` shifts `xc`/`yc` by only ~4354 out of a ~16384 rounding threshold in `convert_to_trans_prec` -- **it does not flip the rounded mv for this block** (confirmed empirically: 417 -> 416 mismatches, same first offset, same magnitude, before/after the fix). So it is real but not sufficient, and not the seed-43 root cause.

Re-derived `gm_get_motion_vector`'s output for block `mi=(8,0)`, `bw4=bh4=8` by hand with the fixed formula: `x=15, y=47`, giving `mv=(-8,8)` -- **exactly what the trace shows** (`mv=(-8,8)`). The mv-stack/mvstack.rs wiring was also independently re-audited against the oracle's `mvref_common.c`: `add_ref_mv_candidate` (75-135, gm-substitutes) maps correctly to `single_ref_match`/`scan_row_compound` etc.; `process_single_ref_mv_candidate`/`process_compound_ref_mv_candidate` (350-472, must NOT substitute) map correctly to our functions of the same name, which correctly use raw `candidate.mv`/`.mv1` with no gm substitution. This wiring is provably correct against the charter's own named concern.

So: entropy in sync, mv computation matches the (now spec-correct) oracle formula exactly, mvstack substitution correctly scoped, motion_mode correctly suppressed (`motion_mode_eligible=0` since `is_global_mv_block && !force_integer_mv`) -- yet the pixel is still off by a small, block-localized, frame-to-frame-growing delta (417 mismatches in frame 1/2, ballooning to ~3900 by frame 23 as the error propagates through the reference chain -- consistent with a systematic per-pixel prediction error, not entropy garbage). Traced this to `reconinter.c`'s `allow_warp` (`~/.cache/aom-oracle/src/av1/common/reconinter.c:33-55`): its `global_warp_allowed` branch is set by the real encoder as `is_global_mv_block(mi, wm->wmtype)` (`reconinter_enc.c:281`) -- the SAME predicate our decoder already computes and correctly uses to suppress `motion_mode`, but which we never feed into the actual per-pixel prediction. `av1_init_warp_params` is called unconditionally for every inter block's predictor build (not gated on `motion_mode`); when `global_warp_allowed` and the global model is valid, it uses the block's FULL affine model (not the block-centre-derived integer mv) to warp-predict every pixel individually. Our decoder's `warp_params: Option<WarpParams>` is populated ONLY when `motion_mode == WARPED_CAUSAL` (local warp) -- every `GLOBALMV`/`GLOBAL_GLOBALMV` block with a non-translation model falls through to plain translational MC using the block-centre mv, which is only a centre-point approximation of the true per-pixel warp and diverges more the further a pixel sits from the block centre -- matching the observed error shape exactly (small at the block's near corner, growing, and compounding across P-frames).
