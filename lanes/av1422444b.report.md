## 2. The cause, localised — 4:4:4-SPECIFIC, and NOT shared with the 4:2:2 family

**It does not share a cause with the 4:2:2 family.** The two defects are different arms
at different depths of the pipeline, and the evidence is not merely that both are
"chroma":

| | 4:2:2 family (`b8eed69f`) | this cell (`f3afa5b7`) |
|---|---|---|
| arm | `sub8_leaf_chroma422` — a SKIPPED INTRABC chroma leaf | `decode_block_rect64` — the 32-capped chroma PALETTE walk |
| what was wrong | the arm took `if skip` and never ran the INTRABC frame copy at its DV | each tiled unit was handed the WHOLE block's palette prediction buffer instead of its own window |
| subsampling reach | 4:2:2 only (`ss_x=1, ss_y=0`) | 4:2:0 is structurally immune (chroma never exceeds 32); 4:4:4 (`ss=00`) is the only shipped format where a 64-axis luma strip's chroma exceeds the 32 cap and gets tiled |
| depth | 8- and 10-bit both | 10-bit only among the shipped sweep cells (the 4:4:4 8-bit cells never tile) |

The mechanism, in the arm's own terms. `crates/ec-av1/src/decode.rs:20051` computes
`(uw, uh) = (chroma_w.min(32), chroma_h.min(32))` and `(nw, nh) = (chroma_w/uw,
chroma_h/uh)`, so at 4:4:4 a 64x64 luma block yields 4 chroma units of 32x32. Both
tiled arms then did `set_palette_pred(<whole block buffer>.clone(), fctx)`, and
`PlaneBuf::reconstruct` reads the first `side * side` entries of whatever it is given —
so unit (0,1) reconstructed the block's row-0 palette values where libaom writes row
32's. `f3afa5b7` routes both arms through `palette_window(pbuf, chroma_w, cu_col * uw,
cu_row * uh, uw, uh)` (`decode.rs:3009`), which re-strides the correct sub-rectangle.

**The sensitive axis is CHROMA UNIT COUNT, not frame width or height** — the census's
own "geometry-sensitive" framing is the misleading part. 352x242 is not special as a
*frame*; what makes this cell bite is that its block structure produces a block whose
4:4:4 chroma is tiled at all. That is why the sibling geometries at the same depth
(320x242 10-bit, 352x250 10-bit, 416x242 10-bit, 416x250 10-bit) were already exact:
their partition search never produced a tiled palette chroma block.

### 3.1 The comparator's liveness, proven before any "exact" verdict was read

`~/.cache/wt444/cmp.py` (shown frames) and `~/.cache/wt444/cmporder.py` (decode order).
Geometry is an explicit argument taken from the cell's own `ffprobe`
`width,height,pix_fmt` — never from a file name, never from a file size. Plane
attribution is per FRAME from that frame's own plane lengths. A wrong SAMPLE is one
`bps`-wide unit. A zero-frame count is a hard error, not a vacuous 0/0/0.

**Control A — one-sample flip, three planes, on the byte-exact cell.** Bit 0 of one
oracle sample's LOW byte, per plane, in decode frame 0. At 10 bit the sample sits in a
16-bit LE container and `2**10 < 2**16`, so +1 is exact by construction.

| arm | Y | U | V |
|---|---|---|---|
| baseline | 0 | 0 | 0 |
| flip Y sample 5 | **1** | 0 | 0 |
| flip U sample 7 | 0 | **1** | 0 |
| flip V sample 9 | 0 | 0 | **1** |

Each arm moves its own plane by exactly +1 and leaves the other two at 0. A comparator
that dropped chroma, mis-attributed a plane, or compared our samples with themselves
fails at least one of these.

**Control B — the two oracles agree with each other.** `cmp ref.yuv aom.raw` (ffmpeg vs
`aomdec --rawvideo`) is byte-identical over all 8177664 B, so the two bases are not
disagreeing about what the pixels are.

**Control C — the mutated tree reds on this exact comparator** (§4), which rules out
the comparator being unable to see a 4:4:4 chroma defect at all.

### 3.2 Three comparator bugs this lane hit, each with its fix

All three were caught by the controls above rather than by reading a verdict, and each
would have produced a CONFIDENT wrong number rather than an obvious failure. They are
the class that produced two wrong tables elsewhere this wave, so the next lane that
writes a comparator should read this list before writing one.

1. **Missing plane offset on the OURS buffer.** The first `cmp.py` indexed the ORACLE
   buffer as `fi * fsz + plane_base + i * bps` but read the OURS buffer as
   `i * bps` — per-plane-zero — so every plane after Y was compared against the wrong
   region. It reported **1362686 / 1362769** wrong chroma samples on a cell that is in
   fact byte-exact, with a first divergence of U(0,0) that was obviously absurd. **Fix:**
   derive ONE `base` per plane and add it to BOTH buffers' indices
   (`a[base + i*bps] != b[fbase + base + i*bps]`); never let the two sides index
   differently. **Tell:** an implausible magnitude, and a first divergence at sample
   (0,0) of a non-luma plane. Note the same class in the other direction — a plane
   offset applied to one side and not the other still moves the count in the right
   direction, so a plausible-looking number is not evidence the instrument is right.
2. **Geometry parsed from the cell's FILE NAME.** The sweep driver read
   `s444_320x240` as `320x320` (the name carries the height after an `x`, so a naive
   split yields width twice) and reported the 4:2:0 cells as `ours=16 ref=8`, which
   reads like a decoder dropping half its frames. It is a name-parsing artefact:
   `ffprobe -count_frames` says 16, and the ref file is 16 frames of 230400 B. **Fix:**
   take `width`, `height` and `pix_fmt` from `ffprobe` on the cell itself
   (`-select_streams v:0 -show_entries stream=width,height,pix_fmt -of csv=p=0`), and
   derive chroma extents as `ceil(w / 2**ss_x) x ceil(h / 2**ss_y)`. **Tell:** a frame
   count that disagrees with `-count_frames`; and a hard error naming both numbers beats
   a tolerated difference.
3. **`bps` hardcoded to 2.** With `bps` fixed at 2, every 8-bit cell's frame size was
   computed at double the truth, so the oracle length stopped being a multiple of the
   frame size ("ref len 3717120 not a multiple of frame size 614400") — an error that
   reads like a truncated oracle rather than a constant. **Fix:** `bps` is an argument
   derived from the cell's own `pix_fmt` (1 byte for `yuv* p`, 2 for `*10le`/`*12le`);
   never infer it from the cell's name or from a "10b" suffix. **Tell:** the
   not-a-multiple hard error, and the fact that it fired ONLY on the 8-bit cells.

The general lesson, which is why the controls are ordered before the verdicts: each of
these three is a comparator that reports a number rather than refusing to. A comparator
that hard-errors on a geometry it cannot account for would have caught all three at the
first cell instead of after a sweep.
