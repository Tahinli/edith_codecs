# lane/h264hi444 report

## What ec-h264 now decodes

- Monochrome (chroma_format_idc 0), High profile and up, 8/9/10 bit. Output is I420 (8 bit) or I010 (9/10 bit) with the chroma planes filled with the neutral value (1 << (bd-1)). ec-core has Gray8/Gray16 but I did not use them: edith's `Deep::load` and the 8-bit path already handle I420/I010, so no edith change is needed for monochrome.
- High 4:4:4 Predictive (profile 244), 8 and 9/10 bit, CAVLC and CABAC, 8x8 transform, scaling matrices (12 lists), PAFF and MBAFF, weighted prediction, PCM. Output I444 (8 bit) / I410 (9/10 bit).
- CAVLC 4:4:4 Intra (profile 44) and High 4:4:4 Intra: same path.
- `separate_colour_plane_flag = 1`: three independent monochrome decode sequences (one Core per colour_plane_id, scaling lists of the plane), merged into an I444/I410 frame on output (`merge_planes` in decoder.rs).
- Lossless: `qpprime_y_zero_transform_bypass` with QP'Y = 0 for all three colours, including the lossless intra prediction DPCM of 8.5.15 (Intra4x4/8x8 horizontal/vertical, Intra16x16 horizontal/vertical, chroma horizontal/vertical in 4:2:0/4:2:2), I16/chroma DC without transform, and the deblocking rule that transform-bypass macroblock samples are not modified (per-edge snapshot/restore; progressive and MBAFF).
- New opt-in `Decoder::set_wide_samples(true)`: accepts 11..14-bit streams. Frames then carry native-depth samples in 16-bit words inside I410/I010 (which only describe 10 bits). Off by default, so product behaviour (refuse above 10 bits) is unchanged. It exists because every JVT 4:4:4 conformance stream is 14-bit.

Design notes
- CABAC: Cb/Cr residual contexts 460..1023 (Table 9-34 categories 6-13) are exactly the luma init values (verified by extracting the tables from libx264); only 1012..1023 (coded_block_flag of 8x8 blocks, 4:4:4 only) are new. Context state array is 1024 wide; `init_contexts` (460) stays for the encoder.
- Residual: new `residual_luma_style` runs luma-style (I16 / 8x8 / 4x4, with 4:4:4 CABAC 8x8 coded_block_flag) per colour component; CBP uses the 16-entry tables for ChromaArrayType 0/3; no intra_chroma_pred_mode; PCM sample counts per ChromaArrayType.
- Inter: Cb/Cr use the luma interpolation with their own weights (no chroma mv derivation); deblocking filters Cb/Cr with the luma filter, luma bS, chroma QP per side.
- `Sps::chroma_array_type()` added in ec-h264-syntax. `slice_bit_depth` became `slice_route` (also peeks colour_plane_id).

## Verification

- x264 sweeps vs ffmpeg byte-exact (tests/high444.rs, 11 tests, pass on server): yuv444p and yuv444p10le, CABAC/CAVLC, 8x8dct on/off, MBAFF 4:4:4, lossless (-qp 0) 4:4:4 8/10 bit, 4:2:0 and 4:2:2 lossless, gray and gray10le. HD case opt-in via EC_H264_HI444_HD=1.
- JVT professional-profile vectors (tests/high444_jvt.rs; fetched into fixtures/vectors/h264-jvt-hi444 by `scripts/fetch-vectors.sh h264-jvt`, checksums in scripts/vectors.sha256):
  - Byte-exact against ffmpeg (gbrp14le): PPCV444I1-3, PPH444I1-3, PPH444P1-5 (14-bit 4:4:4, CAVLC and CABAC, intra and predictive; 120 frames each at 1080p).
  - Mitsubishi streams (PPCV444I4-6, PPH444I4-6, PPH444P6,7,9: 14-bit, separate_colour_plane_flag=1, one with loaded Q-matrix, one with colour_plane_scrambled): decode all frames without error (so the entropy parse is exact end to end) but there is no reference yuv in the archives and ffmpeg refuses separate planes, so pixel exactness is not proven. Visual check of PPCV444I4 frame 0 gives a clean correct image ("card" sequence). I could not obtain JM.
  - PPCV444I-7, PPH444I-7, PPH444P-10 (Sejong Univ.): use FMO slice groups, which ec-h264 refuses by name (outside this lane); the test reports them as skipped.
  - The Hi444 JVT streams contain no lossless stream I could identify; lossless is covered by the x264 sweeps only.
- The three Mitsubishi P/B 14-bit streams and everything above ran on the server.
- Not covered: 4:4:4 Predictive 8/10-bit JVT vectors do not exist in the archive (all are 14-bit); 8/10-bit coverage is from x264 vs ffmpeg.

Monochrome needs no `decode.rs` change (I420/I010 with neutral chroma).

## Limitations

- 11..14-bit only via `set_wide_samples`; luma/chroma depth mismatch still refused; FMO/ASO/data partitioning still refused.
- Lossless chroma DPCM and lossless deblocking protection are implemented from the spec text and verified only through x264 (4:2:0/4:2:2/4:4:4) vs ffmpeg; lossless 4:2:0/4:2:2 chroma edges are not snapshot-protected in the progressive deblocker.
- bS for 4:4:4 uses the luma coefficient flags only; matches ffmpeg on the vectors above.
