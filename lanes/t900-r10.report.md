## STEP 0 -- verdict on the unverified r9 hunk `5c8ab7f2`: KEPT, but only after completing it

Named gates at `6d2ba001` (before any r10 edit), unit `t900-named-r10b`:
`128sb_film interintra hidden_arf rect64_corner_tus sub8 obmc mv_stack
refusal_inventory gate_coverage` -> **34 passed, 0 failed, 1 ignored**
(98.6 s, `$HOME/.cache/t900-named-r10.log`). So the r9 hunk reddened nothing.

libaom, cited: `av1_findSamples` probes the top-right warp sample with
`has_top_right(cm, xd, mi_row, mi_col, AOMMAX(xd->width, xd->height))`
(`mvref_common.c:1235`) -- r9's premise is correct, and it is the ONLY place
that uses the longer side for that probe in a way our port reaches
(`mvstack::has_top_right` has exactly one caller, `decode::find_samples`; the
mv-stack scan's own `bs = AOMMAX(w,h)` at `mvref_common.c:496` is served by the
separate `top_right_scan_allowed`). For a 64x128 block `bs = 32`, and
`has_top_right` returns 0 at once (`if (bs > mi_size_wide[BLOCK_64X64]) return 0`,
`mvref_common.c:270`) -- so YES, libaom uses max(w,h) there and a 128-tall block
gets no top-right warp sample. r9's mi(64,144) analysis stands.

**Why it moved the divergence earlier**: our `has_top_right` port never carried
libaom's two rect shape refinements (`av1_common_int.h:1419-1428`)

    is_last_vertical_rect    = !((mi_col + width)  & (height - 1))   [w < h]
    is_first_horizontal_rect = !( mi_row           & (width  - 1))   [w > h]

which are applied AFTER the mask loop and only bite when `bw4 != bh4` -- i.e.
exactly the blocks whose probe size r9 changed. Probing at the longer side
without them is half a port. Root cause fixed in `b5e1cbde`
(`crates/ec-av1/src/mvstack.rs:705-733`, call site
`crates/ec-av1/src/decode.rs:18995`), NOT reverted.

## Class fixed on the way: ffmpeg pipe deadlock in every gate helper

`ffmpeg_decode_sequence_10bit` (and 6 sibling helpers, one shape, in
`stream.rs` x2, `decode.rs` x2, `tile.rs` x1, `encode.rs` x2) wrote the whole
stream to ffmpeg's stdin INLINE and only then read stdout. With a 1.1 MB
fixture that decodes to ~150 MB the stdout pipe fills first and both processes
park at 0% CPU -- the new gate sat there for 45 minutes before I killed it
(`ps` showed `ffmpeg -f obu -i -` at 0.0% and the test binary at 2.5%).
All 7 now write on their own thread. Same run afterwards: **51.5 s**.
