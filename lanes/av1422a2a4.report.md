## 4. Localization (first wrong symbol)

Both decoders' partition walks agree for the first 36 symbols (byte-identical
`(mi, bsize, value)` prefix, sha256-equal). The divergence at symbol 37
(32x32 partition at mi(40,16): ours HORZ vs oracle NONE) is downstream — the
decoder `tell` had already drifted +963 bits. Rung-by-rung (skill
`ec-av1-first-symbol-divergence`):

- The (32,0) and (32,8) intrabc var-tx trees match the oracle value-for-value
  (`EC_VARTX`/`EC_VARTXCTX` pairing; the earlier apparent ladder fork was
  instrument asymmetry — the oracle's `EC_VARTX` rung prints `bitpos`, not
  `rng`, so those reads were invisible to the rng ladder. Every printed
  symbol still matched → the desync lives in the coefficient phase.)
- `EC_TRACE_COEFF` ladders (deduped rng, `SequenceMatcher`): the last long
  equal block ends at ours[40646]/aom[40596] — inside the mi(32,16) intrabc
  block's own var-tx tree. Read 1 (root, `txfm_split=1 ctx=8`) matches; **read
  2 (sub-unit 16x16 at (32,16) row0col0) is the first wrong symbol**: ours
  `ctx=10`, oracle `ctx=9`, both reading `is_split=0` from different CDF rows.

`EC_VARTXCTX` operand pairing at that read: oracle `above=16 left=16`; ours
`above=16 left=8`. The left operand is `left_txfm[32]` — the TXFM_CONTEXT
band cell for mi row 32, col band of the tree's sub-unit — written by the
PREVIOUS block (the 32x32 intrabc at mi(32,8)).

That block's tree (both sides): split root, 8x8 leaves at (0,0)+(0,4),
16x16 leaves at (4,0)+(4,4). Per-leaf publication leaves
`left_txfm[32..35] == 16` (the 16x16 leaves' height). Our decode wrote 8:
two blanket writes ran AFTER the tree:

1. `decode_block`'s tail `set_txfm_ctxs` (decode.rs:24545, the
   `lane-t900 r32` arm): wrote `logical_tx = leaves[0].2 = 8` over the whole
   footprint, resetting `left_txfm[32..35]` 16→8. libaom's
   `parse_decode_block` tx branch (decodeframe.c:1227-1236) is an EITHER/OR:
   the var-tx branch publishes per leaf via `txfm_partition_update` and
   NEVER calls `set_txfm_ctxs`.
2. `decode_block`'s tail `fill_lf_grid` (publishing variant): same overwrite
   via the deblock-grid publish.

Result: the next tree's sub-read at (32,16) took `txfm_partition_ctx` 10
where libaom takes 9 — the frame's first divergent read — and the desync
surfaced ~30 partition symbols later as the 4x8 subsize refusal at the leaf-8
walk (guard site `decode.rs:37719`, 8x8 VERT at 4:2:2). The subsize guard
itself is honest and was NOT weakened.

**Function ownership**: the fix site is `decode_block`'s tail publication,
NOT `decode_intrabc_owned_rect` (which this lane never touched).

## 5. Fix

`crates/ec-av1/src/decode.rs`, `decode_block` tail — both blanket publishes
gated on the intrabc var-tx tree NOT having run:

1. `set_txfm_ctxs` arm: `if allow_intrabc && !(intrabc_leaves.is_some() && …len() > 1)`.
2. `fill_lf_grid` arm: when `intrabc_leaves.is_some()`, call
   `fill_lf_grid_rect_after_vartx` (deblock grid only, no TXFM band publish)
   — the helper `lane-av1oddheightfork3` introduced for exactly this class.

`allow_intrabc &&` keeps the intra-only-frame behavior byte-identical (no
`allow_intrabc` ⇒ the `set_txfm_ctxs` write was already a no-op restatement of
what the grid did; now it simply does not run, and `record_intrabc_mi`
follows unchanged). A single-leaf tree (len 1) still publishes — libaom's
"unsplit" tree is one leaf covering the block, and the per-leaf publication
wrote exactly the block's own size there, so both spellings agree; measured,
A4's three trees stay correct with this predicate.
