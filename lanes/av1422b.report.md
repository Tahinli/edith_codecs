## Landed (all keyed to reachability only at ss (1,0); 420/444 arms unchanged)

1. `decode_block` tx-size arm: new 4:2:2 branch — the uv plane block is
   `(side/2, side)` (`ss_size_lookup[..][1][0]`), so
   `av1_get_max_uv_txsize` is the SQUARE transform of the smaller dimension
   capped at TX_32X32: 4→TX_4X4 (2x4 rounds to BLOCK_4X4), 8→TX_4X4,
   16→TX_8X8, 32→TX_16X16, 64→TX_32X32, 128→TX_32X32 (BLOCK_64X128 adjusts
   TX_64X64 down). Units stay square; the unit GRID is `(side/2)/tx` wide by
   `side/tx` tall — never square above a 4x4 luma block.
2. All three chroma walks in `decode_block` (skip arm, single-luma-TU arm,
   multi-TU mu-chunk arm) generalized from square `cn x cn` to
   `cn_cols x cn_rows`; each unit's luma anchor split per axis
   (`chroma_tx << ss_x` wide, `chroma_tx << ss_y` tall): `around_mi_rect`,
   `tu_reach_rect` (new helper; keeps the square mismatch counter semantics),
   `record_mi_chroma(cu_mi, span_x, span_y, ...)`, units tuples widened to
   carry both spans.
3. intrabc chroma prediction buffers sized `chroma_side x chroma_height`.
4. `TxbSet::Chroma8`/`Chroma16` `txb_skip` tables widened to six rows:
   rows 3..6 are `av1_default_txb_skip_cdfs[q][TX_8X8/16X16][10..13]`
   (`get_txb_ctx`'s `+10` rows; neutral 16384 in libaom — its encoder never
   reaches them at 4:2:0/4:4:4, a 4:2:2 plane block larger than an 8x8/16x16
   transform does). Mirrors the existing `TXB_SKIP_CHROMA_4_BIG`/
   `CHROMA_32_BIG` assembly. Unused rows are never adapted, so 420/444 CDF
   adaptation is unchanged.
5. `chroma422_square_hits()` made `pub` and printed by `examples/decode_probe.rs`
   (like every other capability counter) for the witness gate later.
6. `EC_PART`/`EC_PART_VAL` traces behind `EC_TRACE` at the 64/32/16/8-level
   partition symbol reads, byte-format-matched to the oracle aomdec's own
   trace (same instrumented-oracle pairing the file already uses elsewhere).

## The 8x32/32x64 leaf note, resolved against the oracle source

`av1_ss_size_lookup[..][1][0]` (common_data.c:17): 16X4→8X4 VALID, 32X8→16X8
VALID, 64X16→32X16 VALID, but 4X16, 8X32, 16X64 (the TALL 1:4 shapes) are
BLOCK_INVALID at 4:2:2. libaom's ENCODER disables exactly those:
`partition_search.c` (`part4_search_allowed`) requires
`get_plane_block_size(subsize, ss_x, ss_y) != BLOCK_INVALID` before a HORZ_4/
VERT_4 may be coded. So aomenc never writes tall 1:4 leaves at 4:2:2 — the
4x16 leaf our decoder tripped on (`EC_RECTCHROMA_GAP` then the closed-shape
unreachable in `decode_rect4_16_strip`) is a phantom partition produced by the
upstream desync above, not a missing portrait block size. Nothing invented;
the shape guard stays closed.
