# lane-av1-444sb — the 128-rect 4:4:4 chroma-span desync: NAMED and FIXED

## Outcome

1. REMEASURED first (pinned fixture
   `crates/ec-av1/fixtures/444_sb128rect_lr_witness.obu`, sha256
   `27825e14633a4b23e37d48a2acdc7f5d814ca4fadd0b8797d72a1ffb34061e80`,
   generated per the report recipe: `ffmpeg -i bands444.y4m -frames:v 3 -vf
   scale=192:160 -pix_fmt yuv444p -f yuv4mpegpipe` piped to
   `aomenc --codec=av1 --profile=1 --passes=1 --end-usage=q --cq-level=32
   --cpu-used=0 --threads=1 --row-mt=0 --sb-size=128 --lag-in-frames=0
   --auto-alt-ref=0 --kf-max-dist=1000 --i444 --enable-restoration=1 --obu
   --limit=3`): at 76f8c3fe frame 0 diverges at EC_AV1_PREFILT_DUMP with
   Y 9700 @ (128,64), U 12272 @ (160,0), V 13175 @ (128,0) — the ticket's
   class (first diffs on the 64/128 grid, chroma columns 160/128 matching
   the finding). The synthetic-content variants tried first (testsrc2,
   testsrc, smptebars, mandelbrot, gradients × cpu-used × cq) all decode
   frame 0 exact — the damage needs an edge-forced 128-root rect, which
   real content provides.
2. DEFECT — **`decode_block_128rect`'s chroma unit walk is hardcoded to the
   4:2:0 mu-chunk span**. One 32x32 chroma unit per 64x64 mu chunk per plane
   (`cn = 32 / chroma_tx` = 1), chunk offsets `ch_col * 32` /
   `ch_row * 32`, and a per-chunk clip step of `ch_col * 8`: all three are
   the 4:2:0 numbers. At 4:4:4 a 64x64 luma chunk covers 64 chroma pixels and
   needs TWO 32x32 units per axis. The units never pushed (measured by
   env-gated per-unit exec tracing): (160,0),(160,32) of the 64x128 PART_VERT
   block at (128,0), all four units of its second chunk, (64,128),(96,128) of
   the bottom-row 128x64 — exactly the PREFILT damage cells. Because the
   missing units' coefficients are still in the bitstream, the entropy
   decoder desyncs from the first 128-rect intra block on: SB(0,0) decodes
   byte-exact and every later superblock of frames 0/1 carries damage.
3. FIX (one site, decode.rs `decode_block_128rect`): per-chunk unit count
   `(64 >> ss) / chroma_tx`, chunk chroma offsets `64 >> ss`, clip step
   `16 >> ss` — every expression reduces to the old constant at ss=1, so
   4:2:0 is bit-identical by construction; the stale
   `debug_assert!` (which stated the 4:2:0 invariant and would fire on 444
   in debug builds) now states the ss-aware one.
4. MEASURED after the fix, same fixture, same instrumented aomdec:
   frame 0 PREFILT 0/0/0 and FINAL 0; frame 1 PREFILT 0/0/0 and FINAL 0;
   frame 2 FINAL 0 — the whole 3-frame stream is byte-exact.
5. Stage-dump hazard worth recording: on frame 2 (pipelined last frame) the
   PREFILT/POSTDEBLOCK/POSTCDEF dumps showed ~7-14k phantom per-plane diffs
   while FINAL was byte-exact — the in-place filters have already touched
   bands the mid-stage dump reads, so for a pipelined frame the mid-stage
   dumps are not a clean stage ladder (class: stage-dump-on-pipelined-frame;
   FINAL is the authoritative byte-exactness rung there). The frame-2
   "divergence" first seen mid-investigation was this artifact plus a stale
   rebuild, not a residual defect; libaom-side confirmation is
   `av1_get_adjusted_tx_size` (blockd.h:1361) capping TX_64X64 chroma at
   TX_32X32, which is what the fixed walk now implements.

## Decision

- One site, fixed. `decode_block_128rect` serves the kf PART128 HORZ/VERT
  and AB arms plus the intra-in-inter 128 path (`in_inter` flag) — one walk,
  all callers covered.

  open defect: one TX_8X4/4X8 unit where the oracle codes four TX_4X4 at

  an experiment changed nothing on this stream and was reverted
