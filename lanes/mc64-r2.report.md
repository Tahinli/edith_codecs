## 1. What the defect was

Charter defect (r1 handoff): `crates/ec-av1/fixtures/av1_192x128_8bit_intra64_in_inter.obu`,
decode-order frame 2, mi(16,32), 64x64 `PARTITION_NONE` INTRA block inside an INTER frame --
3720/4096 luma samples wrong (-12..+9), chroma bit-exact, decode then dying at frame 3 on
lane-intra64split's "a split intra strip whose transform unit is 64x32" refusal.

None of the six charter suspects (tx_depth granularity, 64x64 edge availability, edge filter
with inter neighbours, TX_64X64 coded corner, palette-at-64, delta_q) is the cause. The cause
is the one lane-sbrect10 found (`9f1f108`) and lane-sqdrift confirmed by ablation (`7d498c0`):
libaom `is_cfl_allowed` (`blockd.h`, spec 5.11.5: `block_size_wide[bsize] <= 32 &&
block_size_high[bsize] <= 32`) excludes a 64-axis block from CFL, so its `uv_mode` comes off
the 13-symbol `uv_mode_no_cfl` alphabet. We read the 14-symbol CFL one -- same `DC_PRED`
value, different interval narrowing (class `wrong-alphabet-same-value`). The luma-only,
chroma-exact signature that pointed r1 at the 64-length luma transform is a red herring: the
desynced tail happened to leave chroma intact on this frame, and the frame-3 refusal was a
phantom of our own desync (class `refusal-from-own-desync`).

`decode.rs:6270` and `decode.rs:18781` (`cfl_allowed = bw.max(bh) <= 32`) arrive with the
merge; the merge conflicts I resolved were in the per-frame dump index (kept r1's shared
`stage_dump_idx()`) and two test blocks appended at the same point (both kept).
