# lane-t900 r11 handoff -- target A was NOT loop restoration: it was the mv-stack frame-edge clamp, computed in `usize`

Tip: `2b56599b` on `lane-t900` (r10 tip `2aa87a34`, merged to main as `99692ed0`; main
fast-forwarded into the lane before any edit).

## Target A -- 4K decode frame 88, 221 bytes: ROOT CAUSE FOUND, FIXED, gated

**The charter premise (self-guided restoration last stripe) is DEAD.** The stage
bisection killed it in two runs: the 221-byte mismatch is already present in the
PRE-loop-filter dump, so no filter stage is involved.

* post-deblock dump (`EC_AV1_POSTDEBLOCK_DUMP16` both decoders): rows 1594..1605 differ.
* pre-filter dump (`EC_AV1_PREFILT_DUMP16` both decoders): Y rows 1600,1601,1602,
  x 1472..1535 -- exactly one 64x64 block -- plus 4 chroma samples.

Ladder: `EC_TRACE_MODE` both decoders at decode frame 88 (ours labels frames with
`EC_PICT idx=`, aomdec does not -- locate its lines by matching our `rng`):

    aomdec  EC_MODE     mi_row=400 mi_col=368 rng=32962
            EC_MODE_MV  mode=16 mv0=(32,568)  rng=42514
            EC_STACK    ref=1 i=0 this=(192,-320) w=2
    ours    EC_MODE     mi_row=400 mi_col=368 rng=32962 is_inter=1 skip=1 side=64
            EC_STACK    ref=1 i=0 this=(384,-320) w=2
            EC_MODE_VAL mode=16 mv0=(224,568)  rng=42514

Identical range at both rungs -- the entropy stream never diverged, only the
reconstructed MV. `EC_TRACE_TPL` on both showed every temporal candidate at that
block is `mfmv0=(0,0)`, so the stack entry is not temporal-projection related.

Root cause (`crates/ec-av1/src/mvstack.rs:807` `clamp_mv_ref`): libaom's
`mb_to_right_edge`/`mb_to_bottom_edge` (`set_mi_row_col`, av1_common_int.h) are
SIGNED and a block overhanging the frame's right/bottom edge keeps its full
`bw4`/`bh4`. Frame height 1608 -> `mi_rows == 402`, so the 64x64 block at
mi_row 400 has `mb_to_bottom_edge = (402-16-400)*4*8 = -448` and the window top is
`-448 + 512 + 128 = 192`. We computed that with `usize::saturating_sub` -> 0, window
`640`, so 384 passed through unclamped. Full-pel MV, so the block is a straight copy:
with row 224 (28 px) every source row was past 1607 and our MC replicated the last
reference row; libaom with row 32 (4 px) reads real reference rows 1604..1606 of
decode-order frame 83 (verified by patch search: `f88[1600:1603,1472:1536]` occurs
exactly once in the reference set, at frame 83 row 1604 col 1543 = mv (4 px, 71 px)).

Fix `2b56599b`: both edge terms computed in `i32`; new counter
`mvstack::mv_clamp_edge_overhang_hits` (printed by `decode_probe`).
