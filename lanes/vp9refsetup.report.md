### Semantics ported (bug-for-bug, libvpx 1.15.0)

* `vp9_setup_past_independence` (`vp9/common/vp9_entropymode.c:424`) is called
  for intra-only frames, but `cm->frame_type != KEY_FRAME`, so the stored
  contexts are reset only for `reset_frame_context` 2 (selected) / 3 (all) or
  error-resilient mode. The ACTIVE context is then
  `*cm->fc = cm->frame_contexts[frame_context_idx]`
  (`vp9_decodeframe.c:3008`) — storage, not the defaults.
* Partitions for intra-only (and key) frames come from the const
  `vp9_kf_partition_probs` (`set_partition_probs`, `onyxc_int.h:367`), which is
  NOT a `FRAME_CONTEXT` field: the stored context's `partition` survives the
  frame untouched (restored before storing).
* Reference refresh is `refresh_frame_flags`-scoped; `show_frame` stays 0 (an
  intra-only frame is never displayable — the parser only reads `intra_only`
  when `show_frame == 0`).
* Scaling: `x_scale_fp = (other << 14) / this`, `x_step_q4 = scaled_x(16)`;
  the block maps with `scale_value_x/y`, the MV with `vp9_scale_mv`
  (`vp9_scale.c:29`), and `sf->predict[subpel_x != 0][subpel_y != 0]` picks the
  kernel (`vpx_scaled_horiz/vert/2d` == the step-aware convolve helpers).
  The tap-padding branch is `subpel || step != 16`; the direct read keeps the
  pre-padding coordinates.

## Fixtures and generators (reproducibility)

None of these can be produced by an ffmpeg invocation:

* **intra-only**: libvpx's encoder emits intra-only frames only through its SVC
  path (`set_intra_only_frame`, `vp9_ratectrl.c:2211`), which ffmpeg does not
  expose. Generated by `lanes/vp9refsetup/gen_intraonly.py` from a plain
  ffmpeg keyframe GOP:
  ```
  ffmpeg -v error -y -f lavfi -i testsrc2=size=320x240:rate=24:duration=0.4 \
    -c:v libvpx-vp9 -g 999 -auto-alt-ref 0 -crf 32 -deadline good -cpu-used 4 \
    -pix_fmt yuv420p -f ivf S.ivf
  python3 lanes/vp9refsetup/gen_intraonly.py S.ivf intraonly.ivf
  ```
  The generator reproduces the committed `tests/data/intraonly.ivf` byte for
  byte (`cmp` verified). 11 frames: keyframe, hidden intra-only twin, 9 inter.
* **size change**: libvpx's encoder resizes only through rate control
  (`vp9_resize_one_pass_cbr`, `vp9_ratectrl.c:2728`); ffmpeg exposes neither
  `rc_resize_allowed` nor SVC, and ffmpeg's rawvideo output size is locked to
  the first decoded frame (see the oracle caveat), so a two-size stream cannot
  be dumped in one pass. Generated by
  `lanes/vp9refsetup/gen_scaledref.c` (links the pristine libvpx 1.15.0
  encoder):
  ```
  gcc -I<libvpx> -I<libvpx>/vpx gen_scaledref.c <libvpx>/libvpx.a -o enc -lm -lpthread
  ./enc scaledref.ivf 1280 720 10 200      # one-pass CBR, 200 kbps, lag 0
  ```
  libvpx's force-downsize rule (`>= 1280x720` input and
  `avg_frame_bandwidth < 300000/30`) downscales frame 1 to 640x360 against the
  1280x720 keyframe — a genuine 2x reference scale (`x_step_q4 == 32`).
* **odd variant**: `scaledref_odd.ivf` is `scaledref.ivf` with the keyframe's
  size fields patched 1280x720 -> 1279x719 (mi-grid invariant, so the tile data
  stays valid) — the reference is then an odd coded extent and its chroma crop
  ceils. Patch with the existing
  `$HOME/.cache/vp9pix/patch_kf_size.py <in> <out> 1279 719`, which rewrites the
  IVF container size as well (`sha256 af289a0f8dd91bfa854adeac1814dc77644ad87b9df0af884d33abaae2595413`).

## Oracle caveat (why the committed tests skip frame 1)

ffmpeg locks its rawvideo output size to the FIRST decoded frame's, so a
two-size stream cannot be dumped in one pass: frames 1..N come out upscaled to
1280x720. The tests decode frame 0 alone (`-frames:v 1`, identity) and frames
2..N with `select=gte(n,1)` at the small size, where the filtergraph has
re-initialised and every frame passes through unchanged. The size-change frame
(file frame 1) is the one ffmpeg mangles during that re-initialisation, so it
is covered INDIRECTLY: every later frame predicts from its reconstruction (a
wrong scaler fails frames 2..N). Frame 1 itself is covered directly by the
crate-level `drv_pix3` comparison in gate 3.
