### 1a. THE aomenc SPELLING THAT MATTERS: `--profile=2` on 12-bit 4:2:2 FAILS

This is the reproducibility trap in this cell family and it costs an hour if unknown.

```
$ aomenc --profile=2 --input-bit-depth=12 --bit-depth=12 ... 422p12.y4m
Warning: Assuming --pass=1 implies --passes=1
Failed to set chroma subsampling x: Unspecified internal error      (exit 1)
```

It is **not** that aomenc refuses 12-bit 4:2:2 — it is the `g_profile == 2` branch at
`apps/aomenc.c:2269-2282`, which for a `FILE_TYPE_Y4M` 12-bit input reaches for
`AV1E_SET_CHROMA_SUBSAMPLING_X/Y` on an already-initialised encoder and gets an error
back. 12-bit 4:2:0 at `--profile=2` hits the same call and succeeds, because 420's
`dst_c_dec_h/v` are 2/2 and 422's are 2/1 — the call only misbehaves for the 4:2:2 value.

Measured matrix (same y4m, `--limit=2 --pass=1 --cq-level=24 --threads=1 --width=320 --height=242`):

| command | result |
|---|---|
| `--profile=2 --bit-depth=12 --input-bit-depth=12` (4:2:2 y4m) | **exit 1**, `Failed to set chroma subsampling x` |
| `--profile=2 --bit-depth=12 --input-bit-depth=12 --input-chroma-subsampling-x=1 --input-chroma-subsampling-y=0` | **exit 1**, same |
| `--profile=2 --bit-depth=10 --input-bit-depth=12` | **exit 1**, same |
| `--profile=2 --bit-depth=12 --input-bit-depth=10` | **exit 1**, same |
| `--profile=0 --bit-depth=12 --input-bit-depth=12` | **exit 0**, `Warning: automatically updating to profile 2 to match input format.` |

**Every 12-bit cell here was therefore produced with `--profile=0`, which auto-upgrades to
profile 2 on the y4m's own chroma tag.** That answers the assignment's explicit question:
aomenc **does** accept 12-bit 4:2:2 and **does** auto-upgrade the profile; the only thing
it will not do is accept `--profile=2` spelled on the command line at 12-bit 4:2:2.
The resulting bitstream is genuinely profile 2 — `ffprobe` reports
`Professional,320,242,yuv422p12le` for all of them.

### 1b. Superres needs `--superres-denominator=12` AND a matching width, or it silently does nothing

`--superres-mode=1 --superres-denominator=8` encodes cleanly and produces a bitstream in
which **no frame sets `use_superres` at all** (verified through the frame headers, §4).
This is not a 4:2:2 problem — it reproduces at 320x242 with denominators 4 and 8. What
makes it bite is the geometry: `aomenc` floors the coded width to the denominator grid,
and a 320-wide frame with `--superres-denominator=8` needs 40/8 = 5 coded columns ×8, which
the mode-1 selection rejects. `--superres-denominator=12` at 320 and 256-wide input does
engage it, and matches the shape the repo's own committed superres fixtures have
(`crates/ec-av1/fixtures/444_lossy_superres_256x128_d12.obu`: `size=171x128 up=256
superres=true/12`). **A superres cell that was not checked in the frame headers is not a
superres cell.**

### 1c. Odd-width source construction

`ffmpeg -pix_fmt yuv422p12le` cannot emit an odd width (it silently returns a 320-wide
frame for a `-size 321x242` request; measured 309760 B, which is 320x242's frame size,
not 321x242's 311212 B). The odd-width cells are therefore built by hand: encode a
322-wide (and a 324-wide) 12-bit 4:2:2 y4m, then crop the luma plane to the odd width and
the two chroma planes to `ceil(w/2)` columns per row. Script kept at
`/home/tahinli/.cache/hbd422/trimodd.py`, source y4m sha256 in §2.

## 5. WHAT THIS DOES AND DOES NOT CLOSE

**Closes:** R3 and R9 as *coverage gaps*. The risk study's claim was that no 12-bit 4:2:2
cell and no superres 4:2:2 cell exists anywhere, so neither format had ever been decoded
here. Both are now measured byte-exact against ffmpeg.

**Does not close, and is not touched by this lane:**

1. **R8's "no 4:2:2 unit census".** Still true and still a prerequisite for the lift's
   non-vacuity gate: `set_census_444` arms the unit counters at `ss (0,0)` only, so
   `census_444_units()` reads `[0,0,0]` on every cell in this report. The `chroma422_*`
   counters above are the only 4:2:2 arm-reachability signal the tree currently has, and
   they cover a subset of arms. Anyone writing the post-lift exactness gate should gate on
   one of the `chroma422_*` counters (they are `> 0` on every cell here) rather than on
   the 444 census.
2. **R2, film grain.** This lane produced no `--film-grain-test` cell at all, so
   `film_grain.rs`'s 4:2:0-only geometry is unmeasured here — that arm belongs to
   `lane/av1422grain`. Nothing in this report says anything about it.
3. **The seven known-diverging 8-bit cells (R4).** Untouched; they are not in either
   coverage question and the corpus controls re-confirm `s420_320x242` and
   `s422_320x242` are still byte-exact on this build.
4. **`refusal_inventory.rs:2129-2148` (R7)** and the residual `(0,1)` assertion (R11).
   Source-level, not measurement-level; untouched.

**No divergence was found, therefore no arm was localised and nothing was fixed.** The
reserved group-tail chroma SKIP arm, `film_grain.rs`, and `decode_rect4_16_intrabc` were
not edited.

## 7. ONE-LINE VERDICTS

- **12-bit 4:2:2 — CLEAN.** Byte-exact vs ffmpeg `yuv422p12le` at 320x242, **321x242 (odd
  width)**, 323x243 (odd width *and* height) and 320x242 lossless; Y=U=V=0 on every frame;
  324/324 liveness arms pass. R3's "zero coverage" is now measured coverage. No defect to
  attribute.
- **Superres 4:2:2 — CLEAN.** Byte-exact with `use_superres=true`, `superres_denom=12`
  confirmed in the frame headers, at 320x180 and 256x128 in 8-bit and 256x128 in 12-bit;
  `predict_scaled` 3070–4066 per stream including sub-8x8 inter and 8x8 leaves under a
  scaled reference, so the upscale path is genuinely exercised. R9 closed. No defect to
  attribute.
- **aomenc and 12-bit 4:2:2 — one spelling caveat, not a capability gap:** `--profile=0`
  works (auto-upgrades to profile 2); `--profile=2` spelled explicitly fails with
  `Failed to set chroma subsampling x` at `apps/aomenc.c:2269-2282`. Use `--profile=0`.
- **aomenc and superres — one silent-no-op caveat:** `--superres-mode=1
  --superres-denominator=8` at 320-wide input encodes cleanly with `use_superres=false`
  on every frame. Always read the flag back out of the frame headers before believing a
  superres cell.
- **Nothing was fixed**, because nothing diverged. The decoder source is untouched and
  the guard stands; this report adds coverage, not a fix.
