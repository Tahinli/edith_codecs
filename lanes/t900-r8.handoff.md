# lane-t900 r8 handoff -- inter blocks never stamped the mode maps (edge-filter type); one U sample and a frame-49 cliff still open

Branch `lane-t900`, fix commit `1d928d6e` (merged main `76b33796` first,
fast-forward). No suite this round (turn cap); `cargo check -p ec-av1` clean and
the 128-SB witness gate passes with the new counter.

## Root cause CLOSED this round

**An INTER block wrote neither luma nor chroma mi mode map**, so a later intra
block's `get_intra_edge_filter_type` (spec 7.11.2, libaom `reconintra.h`
`is_smooth`) found no mi-exact entry for an inter neighbour and fell back to the
coarse SUB band, which still held a SMOOTH mode from an earlier block in that
pixel row/column. libaom answers "not smooth" for an inter neighbour by
construction (`mbmi->mode` is an inter mode; `is_smooth(.., plane>0)` returns 0
outright -- "uv_mode is not set for inter blocks"). Wrong filter type =>
`intra_edge_filter_strength` 3 instead of 2 (and `use_intra_edge_upsample` can
flip with it).

* Fix: `decode.rs` `record_inter_rect_mi` -- `if is_inter { record_mode_mi(..,
  DC_PRED); record_uv_mode_mi(.., DC_PRED); }`. The main inter path already went
  through `record_rect_mi`; the gap was every path that only called
  `record_inter_rect_mi` (notably the 8x8 leaf at decode.rs:27273).
* Counter: `inter_neighbour_not_smooth_hits()` (decode.rs, next to
  `uv_mode_mi_override_hits`), incremented in `modes_above_left` (luma) and
  `smooth_uv_neighbour_unsnapped` (chroma) when the coarse band would have said
  SMOOTH and the mi-exact map does not. Asserted `> 0` in the witness gate
  `a_10bit_128sb_film_frames_with_warp_cdef_and_interintra_decode_pixel_exact`
  (stream.rs): **375 hits, 15 shown frames still pixel-exact**.
* Instrument added: the SQUARE-block `OUR_PRED` print now carries `ft=` like the
  rect one (decode.rs:11055) -- that single field is what localised this
  (aomdec `EC_PRED ... ft=0` vs ours `ft=1`).
* Evidence, `~/.cache/rectres-tmp/t6300.obu` (10-bit 1920x792, 125 decode
  frames), `cmp.sh`: frame 11 was 28 Y + 3 U + 4 V samples off; now Y and U are
  EXACT, V has 2 samples left. Whole-cut differing bytes **18108 -> 12780**,
  differing frames 87 -> 86.
  Localisation: prefilter dump identical to the final dump => reconstruction,
  not loop filter; block mi(24,348) is a 16x16 D67 intra-in-inter block,
  p_angle 61, aomdec ft=0 / ours ft=1.

## Open, with what is known

1. **t6300 frame 11 residue**: V only, chroma (673,394) and (674,392), both -1.
   Bottom chroma area (chroma height 396). Same shape as (2) -- treat as one
   defect.
2. **t900 frame 41** (`~/.cache/t900-tmp/cut_900.obu`): ONE U sample. NOTE the
   coordinate moved with the loop filter: **prefilter it is chroma (353,395)**,
   post-filter (354,395), delta -1. So it is RECONSTRUCTION, not
   deblock/CDEF/LR (pf.sh proved this: `pf_r8_900` frame 41 differs the same
   way). The block is mi(192,176), 32x32, `skip=1`, INTER, ref0=5, mv0=(-4,14),
   interp SMOOTH/SMOOTH -- so a pure chroma MC value on the LAST chroma row
   (395 = 792/2 - 1). Its chroma MC call is
   `EC_MC_CALL x_q4=5646 y_q4=6140 w=16 h=16 xfrac=14 yfrac=12 hk=Smooth
   vk=Smooth tw=960 th=396 stride=960`; the vertical 8-tap reads rows 391..398
   and rows >395 are clamped by `mc.rs::sample`. Next step: dump the 8 tap rows
   and the intermediate for column 353 from both decoders (aomdec has no MC
   rung -- either add one to `dec_build_inter_predictors` or recompute by hand
   from the aomdec dump of the reference frame) and check the clamp/rounding on
   the clamped taps. Only one column differs because the error is a rounding
   tip, not a whole-row offset -- do not conclude from "one sample" that the
   row is otherwise right.
3. **NEW, not in the r7 handoff -- t900 cut frame 49 cliff**: `cut_900.obu` has
   264 decode frames (not ~50). Frames 42..48 are exact, then frame 49 differs
   in 1.78 M bytes and it never recovers (every later frame 2-4 M bytes off).
   Checked: it is NOT a frame-order offset (our f49 vs aomdec f48..f52 all
   differ by >1.7 M). This is a full desync/gross mis-decode and is now the
   biggest single item on this stream -- localise it BEFORE spending more
   rounds on the single-sample residues.
