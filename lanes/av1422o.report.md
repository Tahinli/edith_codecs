## Outcome

1. Step 1 of the charter (print before adding): with the header refusal
   temporarily bypassed (probe-only, restored byte-identical — see below),
   the refusing shape printed as `(cw,ch)=(2,16) ss=(1,0)`. The walk's own
   `(2, 16)` is the EVEN strip's own chroma — a shape libaom never codes.
   The port does not chunk it; it is UNREACHABLE after the fix.
2. `decode_rect4_16`'s `has_chroma` is per axis now: a VERT 4x16 strip (1 mi
   wide) keeps libaom `is_chroma_reference`'s column clause
   `(mi_col & 1) || !(bw & 1) || !ss_x`, which with bw == 1 mi reduces to
   `mi_col odd` at every ss_x == 1 format. The old `i % 2 == 1 || ss_y == 0`
   marked even strips as chroma references at 4:2:2 — the source of the
   phantom (2, 16). HORZ strips keep `i % 2 == 1 || ss_y == 0` (all four
   strips are references at ss_y 0); 4:2:0 and 4:4:4 resolve to the exact
   same flags as before in all four strip/format combinations.
3. `decode_rect4_16_strip`'s own-chroma arm is HORZ-only now; a VERT strip
   falls through to the pair merge `((lmi.0, lmi.1 - 1), 8, 16)` — the
   closing strip codes the pair's chroma at the pair's origin
   (`setup_pred_plane`'s `mi_col -= 1` snap), giving (cw, ch) = (4, 16) at
   ss(1,0). The old comment claiming "a conformant stream carries no such
   leaf" is disproven by the fixture itself and is gone.
4. The (4, 16) at ss_x == 1 is CHUNKED the way the pinned oracle walks it
   (`chroma422_pair16` arm): `ss_size_lookup[BLOCK_4X16][1][0]` is
   BLOCK_INVALID (common_data.c row `{ { BLOCK_4X16, BLOCK_4X8 },
   { BLOCK_INVALID, BLOCK_4X8 } }`), so `av1_get_tx_size` reads
   `max_txsize_rect_lookup[255]` — the out-of-bounds byte is TX_4X8
   (skill-measured, 0x05) and `av1_get_adjusted_tx_size` has no TX_4X8
   case. `decode_token_recon_block` then walks unit_width =
   ROUND_POWER_OF_TWO(1, 1) = 1, unit_height = 4, stepr =
   tx_size_high_unit[TX_4X8] = 2, stepc = 1: TWO TX_4X8 units per plane,
   plane-major, the lower one predicted off the upper one's samples. The
   skip arm walks the same two units (prediction runs per unit regardless
   of `skip_txfm`). No coefficient-table row was added: the units ride the
   existing `(4, 8) => ChromaRect8x4` entropy class via
   `read_rect_chroma_unit`.
5. The chunk's `txb_skip_ctx` rides the same INVALID lookup: libaom
   `get_txb_ctx_general`'s chroma branch picks the offset (7 vs 10) through
   `num_pels_log2_lookup[plane_bsize] > num_pels_log2_lookup[BLOCK_4X8]`
   with plane_bsize = 255. Measured, not guessed: the pinned Release
   oracle's decodetxb.c code indexes the `num_pels_log2_lookup` copy at
   vaddr `0xc0db70` (objdump: `cmpb $0xb,0xc0db70(%r15)` et al.), and the
   byte at that offset + 255 is 255 → offset 10 → the port's
   offset-7-first tables take `+3` (above + left + 3), the same shape the
   square multi-unit walks already use.
6. No tx_type symbol: only y plane's is transmitted (decodetxb.c "only y
   plane's tx_type is transmitted"); the intra chroma unit's type is
   `intra_mode_to_tx_type(UV mode)` kept by the all-16 ext-tx set — exactly
   `read_rect_chroma_unit`'s own default. CfL parameters are computed once
   per block over the pair's luma (`are_parameters_computed`) and shared by
   both units; the DC-pred cache is dead in this build (`use_dc_pred_cache`
   never set true), so each unit predicts its own DC.
